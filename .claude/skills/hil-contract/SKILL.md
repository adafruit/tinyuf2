# HIL contract

`scripts/hil_test.py` holds the mechanics: roster and source checks, firmware binding, locking, the probe and USB steps, cleanup and the JSON report. Agents call it instead of composing J-Link, mtools or lock commands. This page is TinyUF2's contract under agentrc's `hil` skill, which is read first.

## Hosts/rosters

- One roster per host, `<roster>` in the commands below: `test/hil/ci.json` on the ci.lan rig (`hostname` `ci`, where the CI job below runs), the only tracked roster, and on htpc's bench an optional `test/hil/local.json`, untracked (`.gitignore`), listing only the boards attached there for the work at hand; `hostname` says which you are on. Pulling the untrack removes a clean tracked copy; where the file is absent, `git show 5639f2d:test/hil/local.json` is its last tracked state, never written over an existing copy. Elsewhere a J-Link, ST-LINK or openocd run fails at `install`, where no probe with the roster's serial is found, before anything is written: `cleanup.state` is `untouched` and nothing stays held. An Espressif board without exactly one tty with its route's serial (for a USJ serial, also on the one 303a:1001 with that serial) stops at the runner's probe check, after the lock: a `ran: false` row with `detail` `probe check: ...`, nothing written and nothing held. Both hosts are shared with tinyusb's rosters (its contract's Hosts/rosters: `test/hil/local.json` on htpc, `test/hil/tinyusb.json` on ci.lan): a rig-wide operation holds both rosters' lock names (`hil` Board locks), tinyusb's under the names and in the sequence its contract's Reservation gives.
- ci.lan has no build toolchain: every record it runs is built off the rig and admitted there (Build, Hosted). Its self-hosted runner runs as the dedicated user `ghrunner-tinyuf2`, without sudo, its work dir `/opt/actions-runner/tinyuf2/_work`.
- From htpc, `scripts/hil_remote.py` runs ci.lan's batteries there (Execution, Remote) over agentrc's remote core (`skills/hil/scripts/hil_remote_core.py` of the agentrc `scripts/agentrc.py` selects, Reservation): htpc builds the records, and the rig admits and runs them with its own roster, `test/hil/ci.json`, under the same board locks and beside CI's state root, `/opt/actions-runner/tinyuf2/_work/tinyuf2/hil-state` (hil.yml's `$(dirname $GITHUB_WORKSPACE)/hil-state` under the runner's work dir, which the ssh user reads through its group). Remote attempts run as the ssh user, the CI job as `ghrunner-tinyuf2`; both share `/tmp/tinyusb-hil-locks`, which must be mode 1777 (the farm creates it so). Each remote run is an attempt directory on ci.lan, `~/hil-remote/tinyuf2/<run id>`.

A roster entry is named by its TinyUF2 board (`ports/<port>/boards/<name>`, which also gives the port) and keeps tinyusb's shape (`name`, `uid`, the serial TinyUF2 reports), its flasher (`flasher {name, uid, args}`) agentrc's board registry's (`skills/hil/boards.json` of the selected agentrc, agentrc `hil` Board registry), found by the entry's `probe`, the serial of the debug probe the board is wired to: an entry with `probe` names no `flasher` (one that does is refused), and only a bench board the registry does not hold names its own. The runner, the build's binding (`check_build.py`'s `board_flasher`) and agentrc's `rtt.py`, `pc_sample.py` and `probe_state.py` resolve it the same way, so those resolve a J-Link or openocd entry's probe with `--hil-config <roster> --board <name>`. An ST-LINK flasher names no openocd configuration, so none of them resolves it: `rtt.py` reaches it only with explicit openocd flags (agentrc's `rtt` skill, OpenOCD route), `pc_sample.py` and `probe_state.py` not at all. A J-Link entry has `args` exactly `-device <name>`; the runner uses SWD at 4000 kHz, so pass the same to those scripts, `--interface swd --speed 4000`. An ST-LINK entry has `flasher.name` `stlink`, `flasher.uid` the ST-LINK's USB serial and no `args`, and `tinyuf2.device` names the device, a name the runner holds limits and a chip identity for (`FLASH_LIMITS`, `STLINK_CHIPS`); STM32CubeProgrammer takes no device name, so every session checks the Device ID and NVM size it prints. An openocd entry has `flasher.name` `openocd`, `flasher.uid` the CMSIS-DAP probe's USB serial, `flasher.vid_pid` its USB ID, exactly one `"0xVVVV 0xPPPP"` pair (required: unpinned, openocd's CMSIS-DAP discovery opens every USB device on the host, a wedged one included), and `args` exactly `-f interface/cmsis-dap.cfg -f target/<target>.cfg`, a target the runner holds limits for (`FLASH_LIMITS`), the openocd on PATH providing the cfg; sessions run at the target cfg's own clock (100 kHz for max32665). A WCH entry, a CH32V4x7 on a WCH-LinkE, is an openocd entry whose `args` are exactly `-f target/wch-riscv.cfg` (no interface cfg: the openocd on PATH must have a WCH-LinkE driver that attaches to its chip, hathach/openocd `4c9931a` on htpc and ci.lan), with `vid_pid` `"0x1a86 0x8010"` and `tinyuf2.device` naming its chip family, the key of `check_build.py`'s `WCH_DEVICES` for the board's port (`ch32v4x7`); it runs the WCH battery (Execution). An Espressif entry has `flasher.name` `esptool`, `flasher.uid` the USB-UART bridge's serial (`/dev/serial/by-id/*_<flasher.uid>-if*`), `flasher.args` none or exactly `-b <baud>` (the install's esptool runs at that baud), `tinyuf2.device` the chip, and the top-level `uid` the chip's factory MAC, which is TinyUF2's USB serial. A board with no bridge is reached through the chip's built-in USB-Serial/JTAG (USJ): `flasher.uid` is then the USJ serial in its MAC form, `AA:BB:CC:DD:EE:FF` in upper case, a form no bridge serial takes (a roster serial is otherwise letters, digits, `_` and `-`), and the runner uses agentrc's `openocd_esp` `usj_tty`, the one tty under the one 303a:1001 whose serial is exactly that, resolved as the provider resolves the USJ; none, two or no single tty fails the probe check, and the probe check also lists processes holding that USJ's usbfs node (`usj_node`). Every esptool session over a USJ connects and resets through esptool's own USJ sequence (Limits). The board's battery is its kind, Espressif, whatever route installs it; the route is the transport. The roster holds the board's hardware only; layouts come from the candidate's build (Build). The `tinyuf2` block holds:
- an ST-LINK, Espressif or WCH board's device or chip (`device`), which a J-Link or other openocd flasher's `args` name instead;
- a bench board's lock name (`lock`) when another project names the board differently, as `mimxrt1060_evk` for `imxrt1060_evk`; both runners take that one lock, and the helper's `status`, holder records and the report rows' `lock` show it. It defaults to the board name. A board with `probe` locks as agentrc's registry name for it (agentrc `hil` Board locks), whatever this roster calls it, and a `lock` here must equal that name;
- the commissioned re-entry path (`reentry`);
- an Espressif board's further install routes (`routes`), each `{"flasher": {"name": "openocd_esp", "uid": "<USJ serial>", "args": "-f board/<chip>-builtin.cfg"}}` for the chip `tinyuf2.device` names, with `"commissioning": "pending"` until commissioning clears it (commissioning.md, On an esptool board). The route reaches the chip's USJ through agentrc's `openocd_esp` (`hil` Flashers), and its USJ serial also selects the tty of the route's esptool sessions, as for an esptool `flasher.uid` in MAC form. It shares the board's one lock and entry: `run`, `install` and `restore` take `--route openocd_esp`, chosen before any board access and never switched after a failure, and `run` refuses a route pending commissioning, which installs and restores only. Under a CI job (`RUNNER_TRACKING_ID` or `GITHUB_ACTIONS` set, even empty) the `openocd_esp` route is refused (exit 2) by the provider's `ci_refusal()`, at route selection before any board access and again before the route's first esptool session; `hil_openocd_esp.py end` is not refused. espressif_p4_function_ev's route (`30:ED:A0:E0:C9:02`) is commissioned (bench-history.md);
- for a board whose TinyUF2 signals no disconnect when it comes up after a reset, the per-port-power hub port its USB is on (`usbPower`: `{"hub": "<hub USB serial>", "port": N}`; the serial, not the bus location, so a replugged hub is still found). J-Link boards only. The hub must switch that port's power on its own. `uhubctl` showing `ppps` is a required preliminary check, not proof: a hub with several gangs, or with no power switches, may report per-port switching too (USB 2.0 11.11, 11.11.1). On a ganged hub a cycle removes no power while another port in the gang is powered, and can power the whole gang off when it is the last (USB 2.0 11.11). The board-only lock is relied on only once commissioning has shown VBUS on that port drop and the cycle reach no other port (commissioning.md, Port power). While `dfu` waits, the runner power-cycles that port, under the board's own lock (Limits), once it has sat connected but unaddressed (sysfs state `default`) for 2 s of that wait, at most once per 10 s, and at no other time: it writes the port's sysfs `disable` 1, then 0 a second later, which the kernel runs under the hub's lock, after any enumeration in progress, disconnecting the child before VBUS goes off. Each write and read-back runs in a bounded child; a cycle that fails or is interrupted from the off write on still writes 0, unless one of its children survives SIGKILL and so could still write after it, and says in `hil.log` whether that restored power or was not attempted. The report lists the cycles (`portCycles`).

The battery runs a board only after commissioning sets `reentry` and confirms `uid`; `install` and `restore` work without `reentry`, for commissioning. Only commissioned roster boards can be offered for a run: an entry without `reentry` is pending commissioning, which CI never runs (Execution, CI). Adding a board is commissioning, the lead's (`commissioning.md`), never a review-time or dispatch-time action: the runner refuses a build record from a dirty tree, an uncommitted roster entry included.

## Selection

`python3 .claude/skills/build/scripts/check_build.py --select-only (--diff-file <file> | --base <ref> [--worktree]) --hil-config <roster>` adds `hil.{boards, full, uncovered}`. Run the battery when `full` is set or `boards` is non-empty. An empty diff file selects nothing; a caller without the changed-file list passes `--base`. `uncovered` names what no roster board on this host can run; report it, never treat it as covered. An app source (`apps/`, `ports/<port>/apps/`) selects no board and is uncovered, except `dfu_runtime`, which selects the Espressif boards of the ports that build it, and leaves uncovered each port that builds it without one (mimxrt10xx today): the battery runs the bootloader with its generated fixture on J-Link and ST-LINK boards and with `dfu_runtime` on Espressif boards. The runner, the build scripts it imports, its lock helper's pin and the roster (`.claude/skills/hil-contract/scripts/`, the agentrc bootstrap among them, `.claude/skills/build/scripts/`, `test/hil/*.json`, the agentrc pin among them) select every roster board; a wording change to this page selects none. `hil.boards` names roster boards whatever their commissioning; CI drops the pending ones (Execution, CI).

There are no examples or test names to select: a run is the whole battery on one board, and the board is the only selection.

## Build

```bash
mkdir -p cmake-build/hil
python3 .claude/skills/build/scripts/check_build.py --board <board> --shared --hil-config <roster> > cmake-build/hil/<board>.build.json
```

`<board>` is the roster name, the TinyUF2 board name; it builds with its port's one backend, ESP-IDF on an espressif board and cmake on every other. A fresh worktree, a review worktree included, needs CLAUDE.md's worktree setup (submodules and dependency links) before `check_build.py` can build in it.

The build record is this contract's build receipt: build it on the clean, pinned HEAD with `--hil-config` and pass it with `--build-record`. `--hil-config` binds the build's own flash target to the roster's probe or bridge (build contract), a build-time compatibility check, and binds each route in `tinyuf2.routes` to the segments that binding hashed (`flashRoutes`); the run refuses a record whose binding names another flasher or route, and checks the files the install reads against the record. The runner never runs the target: it passes the bound files to agentrc's flash provider (Execution). The build dir's lock covers the install's inputs only: the files the runner reads itself (the BIN it verifies, the segments it reads back, `apps/blinky.uf2` and `apps/dfu_runtime.uf2`) are copies in the run dir, taken at admission from bytes that hash as recorded, so a rebuild after the target cannot change them. For a J-Link, ST-LINK or openocd board it must be a cmake build, and its board facts (flash base and size, app start, USB ID, board id, family, vector count, RAM, the double-tap register, delay and magic, the update sector) come from that build: the record also hashes `tinyuf2.elf`, `board_facts.o` (`scripts/board_facts.c` compiled with the exact compile command of the bootloader's `src/main.c`, without LTO, never linked) and blinky's ELF and map, and the runner reads them with `scripts/board_facts.py` from its own copies, checks the BIN against the image the ELF lays out, the HEX against the BIN, the device descriptor against the USB ID, the BIN's `Board-ID` and blinky's vector table at the app start, and refuses any fact it cannot establish. A record without them is refused; rebuild it. An Espressif board's facts still come from the candidate's source. For an espressif board it must be an IDF build from CI's `espressif/idf` image (for ci.lan built off the rig: Hosted below); the run binds its generated `sdkconfig`, `flash_args`, the four segments (bootloader, partition table, otadata, `tinyuf2.bin` in the factory partition) and `apps/dfu_runtime.uf2`, and checks every segment against the generated partition table and the candidate's partition CSV. The run refuses a build record that is not clean, does not match the checkout now (HEAD, submodules, `get_deps` dependencies at their pins), or whose artifacts changed since. Beside its `input`, never a firmware input, the record binds `agentrc`, the portable identity (commit and closure digests) of the agentrc the build loaded (Reservation), refused at the build when a closure file changed since it loaded; every admission (the runner's, `hil_hosted.py admit`, a remote driver's) refuses a record binding none or another than the one it loads, whatever agentrc's own dirty flag: rebuild it. Commit first; ESP-IDF's records also go stale at the next commit (build contract).

A remote run (Execution, Remote) builds each board's record here, from the committed identity it freezes, with `hil_hosted.py build` (Hosted below), and the rig admits it into the attempt's rebuilt checkout (`<attempt>/src`) as `<attempt>/out/<board>.build.json`, its build dir inside that checkout (`buildDir` is checkout-relative); the record stays there for recovery.

The Ninja query that inspects a flash target at the build (`ninja -t commands`) is bounded to 30 seconds. A timed-out or interrupted query's process is killed (only that process, which stays in check_build's process group, so a kill of the group reaches it too) and its ESP-IDF container (`tinyuf2-query-<pid>-<32 hex digits>`, unique per query) removed until docker has listed none for 2 seconds; a timeout fails the build naming the build dir, the query and any container that may be left, and an interruption prints that container on stderr. The install runs no Ninja query and no container.

### Hosted

Every record ci.lan runs is built off the rig and admitted there (`scripts/hil_hosted.py`): the CI job's (Execution, CI) on a GitHub-hosted runner, a remote run's (Execution, Remote) on the dev PC that launches it, and a commissioning record from a dispatch (commissioning.md):

```bash
python3 .claude/skills/hil-contract/scripts/hil_hosted.py build --board <board> --roster test/hil/ci.json --out <dir>
python3 .claude/skills/hil-contract/scripts/hil_hosted.py admit --artifact <dir>/<board> --board <board> --roster test/hil/ci.json --out cmake-build/hil
```

`build` runs the Build command above (an Espressif board's in CI's image, which it needs pulled: `hil_hosted.py image` names it; any other board's with cmake, which needs `cmake`, `ninja` and the compiler `.github/actions/setup_toolchain` installs for the board's port on PATH: `hil_hosted.py toolchain --board <board>` names its `toolchain.json` entry, `arm-gcc` (the Arm GNU Toolchain release, tinyusb's 14.2.rel1 today) or, for a RISC-V port, `riscv-gcc` (the xPack riscv-none-elf-gcc release)) and refuses a cmake record whose `compiler` is another (below); it packs `<dir>/<board>`: the record (`<board>.build.json`), every file its row hashes under `build/`, and `provenance.json` (`version`, `board`, `roster`: its path and sha256). On the rig, `admit` refuses (exit 2; the last stdout line is JSON) unless all of these hold:
- the board: provenance names this board, one in this roster;
- the roster: provenance's path and sha256 are this checkout's roster's, which the record does not name;
- the commit, dependencies and IDF: the record passes the runner's own record check here (`hil_test.py` `record_row`): passing, one row of this board, the board's backend (cmake, or IDF for an Espressif board), an IDF build in CI's pinned image (`idf.mode` docker and `idf.image` `espressif/idf:<build.yml's toolchain_version>` read from this checkout, so a local-IDF record is refused as before), HEAD, submodules and get_deps dependencies equal to this checkout's, clean on both sides, and the record's `agentrc` the identity of the agentrc this admission loads;
- the compiler, for a cmake record: its row's `compiler.version` (check_build records the compiler of the bootloader's `src/main.c` from `compile_commands.json` and the first line of its `--version`) names the release `.github/actions/setup_toolchain` installs for the board's port, read from this checkout's `toolchain.json`: the `arm-gcc` url's Arm GNU Toolchain release (`check_build.py` `ci_arm_gcc_release`), whatever the case of its `Rel`, or for a RISC-V port the `riscv-gcc` url's xPack release (`ci_riscv_gcc_release`), whose `--version` omits the xPack build number, so builds of one GCC version are not told apart; another release, another vendor's build or none refuses, as an IDF record from another image does. A local bench record is not held to it: the battery itself takes any compiler;
- the consumed files: the record's build dir is `cmake-build/cmake-build-<board>` (a variant's is another), and its `sha256` names exactly the artifact's `build/` files with their hashes, the artifact holding nothing else; a missing, extra, changed or linked file refuses. Those are every file the battery reads from the build dir: the install's, the board facts' ELF and object, blinky's ELF, map and UF2, the BIN and HEX;
- the flash binding: placed as that build dir under its lock (replacing what it held), the files hash as recorded and the binding names this roster's flasher (`admit_flash`).

It then writes `<board>.build.json` and `<board>.provenance.json` to `--out`. That record is the `--build-record` of `run`, `install` and `restore`, which admit it again as any record; it goes stale at the next commit like any IDF record. On ci.lan a record for a manual `install`, `restore` or recovery is such an admitted one.

## Execution

```bash
python3 .claude/skills/hil-contract/scripts/hil_test.py run -b <board> --build-record cmake-build/hil/<board>.build.json <roster>
```

Before taking the lock, the run checks every span it could write (the HEX the flash target loads, inside the install span and the device's flash limits and laid out as the BIN; the BIN's board id), with the install and app spans taken from the candidate's build facts. Run it in the background; one board takes about 2 minutes, and the run is complete when it exits: its last stdout line is the report JSON (Results). With several boards, one battery per board, one after another.

The battery's steps on one board, all under one lock. The roster's probe serial selects the board (each probe is wired to one target), so no step identifies the chip:
1. **install:** agentrc's flash provider (`hil` Flashers, `flash_jlink`) runs JLinkExe on the record's HEX with the script the record's `tinyuf2-jlink` target runs, `halt`, `loadfile <hex>`, `r`, `go`, `exit` (a test keeps the two equal), from a command file in the run dir, under the build dir's lock once the files it reads hash as recorded. JLinkExe can exit 0 with every command failed, so each command is judged from its own output (commissioning.md, J-Link transcript shape): every command echoed once and in order with its completion line and no failure line, the record's HEX downloaded (programmed, or skipped as already matching) before `loadfile`'s `O.K.`, and the script completed. The files are hashed again after it, and a session of the runner's, through the provider's `run_jlink_commands` with this contract's connection profile, verifies each contiguous run of the HEX at its flash address (`verifybin`), then resets. The install is never retried. The board is touched from JLinkExe's start; only attempts that all end before any target connect leave it untouched, either at "Connecting to J-Link ...FAILED" or in the `libjlinkarm` crash at the probe connect (Limits), and a timed-out one never does. The build dir's lock is released only once every child the flash started has ended: one that outlives SIGKILL keeps it through a keeper that exits once the child does (`buildLocksKept`), so a rebuild waits.
2. **dfu:** the UF2 drive with this board's serial is found. On the RT boards the install has left the app start erased on the bench (Limits), so DFU comes up; if it never enumerates, as when a valid app boots (an install on stm32f303disco, stm32f411ve_discovery or stm32h563_nucleo keeps the app; per-board evidence: bench-history.md), the commissioned `retained-register` re-entry brings DFU up (its claim says so); any other DFU failure fails the step. `INFO_UF2.TXT` must name this build's version and board, and `CURRENT.UF2` must have its size. The double-tap register is then cleared and read back, once the bootloader runs.
3. **copy:** a generated app is copied to the drive.
4. **app-ran:** the probe shows the app counting in thread mode with VTOR at the app start.
5. **reenter:** the bootloader is re-entered by the commissioned path, and the drive's `CURRENT.UF2` reads the app back.
6. **cleanup** (reported as `cleanup`, not a step, state `blinky copied`, or `untouched` with nothing to do when no session reached the board): the record's TinyUF2 is installed again as in install, DFU is found, the record's `apps/blinky.uf2` (admitted with the record: one family, every block in the app region) is copied to the drive, and the DFU device must leave and stay away for a quiet period. A failure ends the run's lock all the same: the board is released and the failure logged in its cleanup log (Reservation, Recovery, exit 4).

On an ST-LINK board the steps are the J-Link board's, each probe session one STM32CubeProgrammer CLI script (`-script`) that connects to the roster's serial in `HOTPLUG` mode, without a reset. A session passes only with exit 0, the roster's Device ID and NVM size, every operation echoed in order with its success line, no `Error` line and the script's end; the CLI stops a script at its first failed operation. `install` runs the provider's `flash_stlink` on the record's HEX, the command the record's `tinyuf2-stlink` runs (`--connect port=swd sn=<serial> --write tinyuf2.hex --go`), whose transcript must show the HEX parsed, the sectors erased, "File download complete" and "Start operation achieved successfully"; a session of the runner's then reads the BIN back from its flash address (`-u`), compares it, and resets (`-rst`). `app-ran` takes both samples, the delay and the image read-back in one script. The SYSRESETREQ write is the provider's `sysresetreq_stlink` (`-w32 … -nv`: with the CLI's read-back the write fails across the reset), and on a J-Link board its `sysresetreq_jlink`; this contract judges both. Only "Error: Serial number not found" before any device line leaves the board untouched.

On an openocd board the steps are the J-Link board's, each probe session one openocd script through the provider's `run_openocd_commands` (`init`, the commands, `shutdown`, the probe selected by serial and USB ID), which attaches without a reset. openocd stops a script at its first failed command with exit 1, so a session passes only with exit 0, "shutdown command invoked" and no `Error` line. `install` runs the provider's `flash_openocd` on the record's HEX, the file the record's `tinyuf2-openocd` programs, without program's verify (`program <hex> reset exit`, the flasher's `verify: false`), as the ST-LINK install drops the CLI's, whose transcript must show program's phases in order, then the shutdown, with no `Error` line; a session of the runner's then halts, reads each of the HEX's runs back from its flash address (`dump_image`), compares it, and ends in `reset run`. `app-ran` takes both samples (`reg pc`, `r0`, `msp`, `xpsr`, the target's names), VTOR, the delay and the image read-back in one script. From a script openocd prints a command's result only when it is echoed, so every value the runner parses is read as `echo [mdw ...]` or `echo [reg ...]` (rig, 0ce743125), and a read-back is `dump_image`'s file, never its printed result. The SYSRESETREQ write is the provider's `sysresetreq_openocd` (`mww` to AIRCR), judged as any session, since the write and the shutdown after it complete cleanly on the bench. Only "unable to find a matching CMSIS-DAP device" with no debug port read (no `DPIDR` line) leaves the board untouched. A timed-out or interrupted openocd is reaped and, when it outlives SIGKILL, kept as a survivor, as a stuck JLinkExe is. The busy check (Reservation) finds the probe's usbfs node under the flasher's USB ID (`vid_pid`).

On a WCH board the steps are the openocd board's, with the RISC-V evidence the CH32V4x7 gives, never an Arm register: the fixture is an RV32 image (`fixture_riscv`) entered by a jump at the app start (the port's `board_app_valid` check), setting its stack and `mtvec` to a trap loop at the app start + 0x400 (unified entry, its base 1 KiB aligned: QingKeV3 manual 3.2) and then counting in `a0`; `app-ran` takes two halted samples of `pc`, `a0`, `sp` and `mtvec` in one session (`pc` in the counter loop both times, `a0` moved, `sp` and `mtvec` the fixture's) and reads the image back. The system reset is openocd's `reset run`, which the backup registers survive (CH32V407RM 3.2.2), and the double-tap register is the 16-bit `BKP->DATAR10`, written with `mwh` on the running core and read back with `mdh`. A `reset run` session may log `Error: [wch_riscv.cpu.N] Polling failed, trying to reexamine` once, as the next poll finds the core reset (bench 2026-11-11); any other error line fails it as on an openocd board. Only `Error: open failed` (no WCH-LinkE with the serial) before the probe's `WCH-LinkE  mode:` line leaves the board untouched. The probe attach does not reset a running core (bench: blinky's counter ran on across sessions). It does stop USB until the next reset, clearing HSEON and USBHS_PLLON (bench-history.md, ch32v407_r0), so no session opens while the battery needs the drive: the install clears the double-tap register before its read-back session, whose `reset run` brings DFU up on the app its chip erase left empty (no retained-register fallback), and `reenter` reads CURRENT.UF2 before the register.

A board's evidence is scoped as the report says. "app-ran" is execution after the bootloader handoff; on a J-Link board a run triggered by the upload alone is unverified (an Espressif board's app-ran observes the copied app itself over USB). "reenter" by `retained-register` is the forced-entry path, not a physical double tap.

On an Espressif board, each esptool connection is a child of the runner, and so is each USB control request (pyusb): the `hil` provider's `esptool_session.py` and `usb_dfu.py` beside `hil_lock.py` in the selected agentrc (Reservation), which admission requires before any board access:
1. **install:** a first connection takes the MD5s of every partition the battery never writes (nvs, ota_1, ffat on the 8 MB layout) as the run's snapshot, kept in the row's `snapshot` however the run ends; that session is the first to touch the board, which only a missing tty with the route's serial leaves untouched. Then the provider's `flash_esptool` runs the runner's own esptool, the `esptool` first on PATH (Limits; refused before any board access without one), as `NO_COLOR=1 esptool --chip <chip> -p <tty> [-b <baud>] [--no-stub] --before=default_reset --after=hard_reset write_flash <flash_args>` from the build dir under its lock, with the same hash checks as a J-Link install. esptool 5.2.0 writes every segment, as `IDF_FLASH_FULL=1` made the IDF target do, and copies none to `*_flashed.bin`. It must exit 0 with none of the failures esptool exits 0 on in its output (the provider's `esptool_problem`). A runner session then reads each segment back and takes those MD5s again, then resets once; the runner compares the read-back bytes with the build's segment files and the MD5s with the snapshot, and any difference fails the step. esptool rewrites the bootloader header from `flash_args`, which the build already holds (dio, 80 MHz, 8 MB): on the bench (2026-10-13, esptool 5.3.1 in espressif/idf:v6.1) all four segments read back identical to the files. The roster's bridge or USJ selects the board (a bridge is wired to that board only; a USJ is the chip's own), so the chip is not identified, and its security eFuses and flash size are commissioning's to check. The evidence lists each write's span and the 4 KiB-aligned span covering it, and the esptool version. Blank otadata boots the factory partition, TinyUF2.

   On the `openocd_esp` route (Hosts/rosters) the install runs under the same one board lock, each step only once the previous one's cleanup completed: an esptool session over the USJ's tty reads the chip's security state on the ROM loader, before the stub, from esptool's GET_SECURITY_INFO and from the eFuse registers (on the P4 SPI_BOOT_CRYPT_CNT and SECURE_BOOT_EN), takes the snapshot and hard-resets the chip, since one left in the ROM loader faults openocd's flash stub after `reset init` (PMP Load access fault at `flash probe`, bench 2026-10-20); the provider's `security_evidence` reads that result, refusing sources that disagree, and its `admit_security` refuses the install, nothing programmed, unless both read flash encryption and secure boot off; the provider records that evidence (`security`, naming the esptool the runner checked). The provider reads the security state of its `SECURITY_CHIPS` (ESP32-P4, ESP32-S3) only, so a route to any other chip (the ESP32-S31, whose eFuse map is undocumented) is refused when the roster loads. Declaring that the runner keeps the board lock through a session left pending (`retains_lock=True`, also checked through the provider's `refusal` before the security and snapshot session), the provider's `flash_openocd_esp`, which starts openocd no earlier than its `BOOT_SETTLE` after the call (bench-history.md, espressif_p4_function_ev JTAG route), programs the record's segment copies, each with the sha256 the build record holds for it (the provider admits only those bytes), in one openocd-esp32 session pinned to the USJ by serial and bus-port (the build `$HIL_OPENOCD_ESP` names, else `openocd` on PATH; the provider refuses any but v0.12.0-esp32-20260703), after a `reset init` whose event hooks all passed, each written and checked with `esp verify_bank_hash` without a reset between, reads each back byte for byte and ends with `reset run` and a confirmed shutdown; it writes the files as built, without esptool's header rewrite, so the read-back compares the built bytes. Then the esptool read-back and preservation check as above. A session the provider leaves not ended is cleanup pending (Results, Recovery): the runner never signals or reaps it, and no later session, restore or retry runs.
2. **dfu:** as above; `INFO_UF2.TXT` reports the app partition (ota_0) as its flash, and no register is written.
3. **copy:** `apps/dfu_runtime` from the record, plus a block carrying a fresh nonce in ota_0's last 256 bytes, where the app reads it, renumbered under one `numBlocks`; the image itself is never patched. The record is refused when the image reaches that block or TinyUF2's 64 KiB flash cache window over it (`FLASH_CACHE_SIZE`) leaves ota_0. The evidence lists the image and nonce spans and the cache windows covering them.
4. **app-ran:** the app enumerates with its own VID:PID and the board's serial on the DFU's USB path, its DFU runtime interface string read from the device is `HIL <nonce>`, and TinyUF2 stays away for a quiet period.
5. **reenter** (`dfu-detach`): DFU_DETACH to the app is acknowledged, the app leaves, TinyUF2 comes back on the same path, and `CURRENT.UF2` reads back the image and the nonce block.
6. **recopy:** a copy with a fresh nonce boots the app again.
7. **cleanup:** as on a J-Link board, with the install as in step 1: the preserved regions' MD5s after the writes, and again after the blinky copy, must equal the run's snapshot (a recovery takes it from the failed report's `snapshot`; a manual `restore` takes its own first). A mismatch fails the cleanup (Recovery, exit 4).

`--fail-at <step>` exists only for acceptance: it fails that step to exercise cleanup.

### Update

`run --update-record <variant record>` runs the update battery in place of the app battery, on a commissioned J-Link board of a port whose `update-tinyuf2.uf2` is the bootloader BIN itself, which the TinyUF2 running from RAM writes in place (`UPDATE_PORTS`: mimxrt10xx, `ports/mimxrt10xx/CMakeLists.txt`). Elsewhere it is refused (exit 2) and self-update stays uncovered (Limits). The variant record is the same clean checkout built beside the candidate's with a define that changes the bootloader's version string, which `INFO_UF2.TXT` must tell apart:

```bash
python3 .claude/skills/build/scripts/check_build.py --board <board> --shared --hil-config <roster> --variant update -D 'CFLAGS_CLI=-UUF2_VERSION -DUF2_VERSION="hil-update"' > cmake-build/hil/<board>.update.json
python3 .claude/skills/hil-contract/scripts/hil_test.py run -b <board> --build-record cmake-build/hil/<board>.build.json --update-record cmake-build/hil/<board>.update.json <roster>
```

Before the lock, the variant record is admitted as the candidate's is (passing, `--shared`, cmake, this checkout, clean, its files hashing as recorded) and its BIN must be this board's, with a version other than the candidate's; each record's `_bin/apps/update-tinyuf2.uf2` must lay out its own BIN from the flash address in 256-byte blocks of one family, numbered under one numBlocks; and the two BINs must hold different bytes at an address both write but their last blocks, in a flash cache sector, the size of the bootloader ELF's `_flash_cache` (4 KiB on mimxrt10xx). The runner reads its own copies of both updaters and of the variant's BIN, taken at admission. The row's `update` names the variant (`buildRecord`, `path`, `sha256`, `version`, `defines`), both updaters' sha256 and `differingSectors`.

The steps, under the one lock:
1. **install**, 2. **dfu:** as the app battery's.
3. **update-variant:** the variant's updater copied to the drive as `copy` copies, its flush recorded, not judged. TinyUF2 writes its own region and resets once the last block is in, and the ROM boots the new bootloader, whose DFU comes up at once (the app start stays erased since the install). That DFU has the old one's descriptors, so the host need not see it leave: usb-storage's error recovery resets the port and keeps a device whose descriptors did not change (Linux `drivers/usb/core/hub.c` `usb_reset_and_verify_device`, which logs "reset high-speed USB device number N"; bench 2026-10-21, run-20261021-202435, where the device stayed number 15). So the drive naming the variant's version within 40 s, read again until it does, is the observation, never DFU leaving; then a probe session verifies the bootloader region against the variant's BIN (`verifybin` at its flash address) and resets, and the drive must name the variant again.
4. **update:** the same with the candidate's own updater, over the variant: the candidate's `update-tinyuf2.uf2` replaced a different bootloader, proven by readback, and the result still enumerates after a reset.
5. **interrupt:** a runner child (`uf2-write`) writes `INTERRUPT_PASSES` alternating passes of both updaters, the variant's first and last, each without its last block, raw to the drive in one O_DIRECT write: TinyUF2 takes a UF2 block wherever it lands (`src/ghostfat.c`), erases and programs each differing sector again on every pass inside the WRITE10 that crosses it (`board_flash.c`), and never completes an image, so it never resets on its own. Once `/sys/block/<dev>/inflight` shows the write in flight, the observable event and never a timed sleep, the probe's SYSRESETREQ session runs. `writeInFlight` holds only when the write call started before that session and returned after it ended (the child's `writeStart` and `writeEnd`, taken around the call itself), so it was outstanding when the session issued the AIRCR write; a write that failed at once or at its open shows no overlap. The overlap is host-side: that the device was erasing or programming at that instant is an inference, since it does so inside the WRITE10 that crosses each differing sector, never an observation (`claim`). Without it the step fails (`NotInterrupted`) once the recover step below has run: the run is no pass. The USB port is sampled from the write's start (`usb`: whether it was ever empty, each device seen) and whatever is there afterwards is recorded (`afterReset`, `vid:pid serial`, or null), none of it required, since the host may keep a device that comes back as the same DFU (step 3): on the RT1010 an internal boot that fails jumps to the serial downloader (IMXRT1010RM Rev 0, 9.3.5, p. 160), and in the open security configuration an image whose authentication fails still executes (9.3.6, p. 160).
6. **recover:** the battery's own install (step 1) installs the candidate again and verifies it, and DFU comes up naming its version: the probe recovered the board. It runs after a failed `interrupt` too, when only the overlap was missing.

The cleanup follows as for every battery; a failed one is exit 4, the board released and the failure logged (Recovery). `--fail-at` takes these steps too. `hil_remote.py` refuses `--update-record`, and CI never passes it: the update battery is a bench campaign. It runs on a host that builds its own records (htpc): ci.lan cannot prepare the variant record, since hosted admission (`hil_hosted.py`) covers the candidate's record only.

### CI

The `HIL` workflow (`.github/workflows/hil.yml`) runs the battery on the ci.lan rig for every pull request from this repository (a fork's never reaches the rig). A hosted job selects the boards the change reaches (Selection, with `test/hil/ci.json`) and prints what is uncovered in its summary; only commissioned boards go on (Hosts/rosters), and a selected board pending commissioning is listed as not run. A second hosted job builds every board the rig will run from the same merge commit, one leg per board (`hil_hosted.py build`, Build, Hosted), each preparing only its own backend: the toolchain `hil_hosted.py toolchain` names, through `.github/actions/setup_toolchain`, whose `toolchain.json` entry names the release admission pins a cmake record's compiler to, or CI's ESP-IDF image; that job, `hil-build`, uploads each board's build as `hil-build-<board>`. The rig job, `hil-run`, on the runner labelled `tinyuf2`, checks out the merge commit without persisting its token (the rig keeps state between jobs), fetches the submodules, agentrc at its pin (`scripts/agentrc.py fetch`) and the selected boards' dependencies, downloads every `hil-build-*` artifact of the run into one directory, and runs `scripts/hil_ci.py --hosted <dir>`: it admits each board from its own `<board>/` there (`hil_hosted.py admit`; a missing or refused artifact is not-run while the other boards run; a leg that failed in this attempt may leave an earlier attempt's build of the same merge commit, which admission checks like any other); and one battery whose run directory (`run --run-root`) lies under the rig's `hil-state/<run id>` with the record and the battery's output, uploaded as `hil-run-<attempt>`. The battery keeps trying a held board every 0.25 s for `run --lock-wait` (10 min from CI), with one last take once its final pause ends (agentrc's `board_task`: a board freed in that pause is taken just past the budget), then reports it locked, which the job reads as not-run, never a pass; an older runner's cleanup holder is never waited for (Recovery, Legacy). The job's pre-flight is its markers; under its lock the runner's busy check follows (Reservation): a surviving `mcopy` or USB helper of a killed run, which the busy check does not see, is seen through the marker, not by a host-wide process scan. Each row maps onto the Verdicts: the job exits 0 only when every selected board passed, 1 on a fail or not-run, 2 on a blocker. Before the upload each run directory's report pair is prepared through agentrc's report core (its Markdown regenerated from the JSON, or an explicit unavailable notice where the JSON is missing or unreadable, never a stale view; when the preparation itself fails, each Markdown is replaced by that notice with the run's view kept below it only as labelled text, or removed, under the core's writer lock; one that can be neither, or whose lock another writer holds, is listed in `summary.json` `unsafeArtifacts`, as is a run root that cannot be listed, and then the upload excludes every `hil_report.md`, as it does when `hil_ci.py` did not finish: its decision, `upload-views`, is written last), and `summary.json` gives each board, beside its `verdict`, the `hil` shared run rules' `sharedVerdict` and `sharedDetail` over that JSON: the same rows, with a run aborted by a signal or a non-empty caveat a blocker and an unreadable or unprepared report a blocker. The job summary labels the native verdict, shows the shared one where it differs or the report was not prepared, and adds the open cleanup failures a battery found on taking its board (`summary.json` `previousCleanupFailure`, `openCleanupFailures`) and what it could not record (`notes`, the report's own `Notes:`: `legacyPending`, `legacyNote`, each `lock.restoreNotes` and the lock's end when notable (Results), a passing battery's included); it never changes the exit. A battery touches its `<board>.started` only once it holds the board, before any hardware access (`run --started-marker`, `hil_ci.py`'s only; a marker it cannot write refuses the run and releases the board), so a run that takes the lock while it still waits never sees it started, and a battery that never held the board leaves no marker. A battery that is no blocker touches its `<board>.done` before it releases the board (`run --done-marker`, `hil_ci.py`'s only), so a run that takes the lock next never sees it unfinished; `hil_ci.py` then keeps that marker only where its own verdict is no blocker and the battery marked its start. A battery that ended without a report or with a blocker, a failed cleanup among them (its lock ended with it all the same), leaves its `<board>.started` marker without a `.done`: that board is a blocker on every later run until recovery (Recovery) has run and the marker is removed by hand; the workflow is never cancelled by a newer push for the same reason. That refusal stays: the busy check is a snapshot of the probe's users only (Reservation), so the marker is the only guard against a killed battery's leftover child that touches the board's USB devices, and it guards only runs that read the same state directory (CI's, or a remote run's `--ci-state-root`), never a manual command or another project's run; an unfinished attempt is never only reported. `workflow_dispatch` runs named commissioned roster boards, with `fail_at` for `--fail-at` and `hosted_fault` (space separated `build:<board>@<attempt>`: that board's build fails in that attempt only, so a re-run with the same inputs can recover; a malformed token fails the selection) for acceptance only, and also builds a named board pending commissioning without running it: its leg's `hil-build-<board>` artifact is what commissioning admits by hand (commissioning.md). On a pull request a hosted `pr-comment` job renders `summary.json` and the select job's selection (`scripts/hil_comment.py`) into one sticky PR comment: per board its steps, blinky cleanup and admission and run times (`summary.json` `buildS`, named from when the rig built, and `runS`), with a note per board that did not pass under both verdicts, one per board whose battery found open cleanup failures or carries `notes`, and an explicit unavailable line where the selection or summary is missing; it downloads the rig's artifact and posts only when this is the newest attempt of the newest HIL run for the PR's current head, so a late older run never replaces a newer report, and never changes a verdict or the exit.

### Remote

From htpc, for ci.lan's roster boards:

```bash
python3 .claude/skills/hil-contract/scripts/hil_remote.py run -b <board> [-b <board> ...] [--run-id <id>] [--lock-wait <s>]
python3 .claude/skills/hil-contract/scripts/hil_remote.py wait <id> [--timeout <s>]
python3 .claude/skills/hil-contract/scripts/hil_remote.py collect <id>
```

`run` freezes HEAD and every repository it pins (the submodules and the get_deps dependencies of the boards' ports, unpushed commits included) as self-contained git bundles, then builds each board's record here from that checkout with `hil_hosted.py build` (Build, Hosted: this PC's `cmake`, `ninja` and CI's compiler release for each board's port, or docker with CI's ESP-IDF image pulled) into the stage as `hosted/<board>`, stages the agentrc this process loaded as `.agentrc/` (agentrc's `agentrc_source.stage`: its closure as regular files, each checked against the digest taken at load, and its manifest), and binds them all by a manifest of the commits, shallow boundaries, roster digest, boards, bundle and driver digests, every hosted file's sha256 (`hosted`) and every staged agentrc file's (`agentrc`). Before anything reaches the rig it refuses a checkout that is not clean, a submodule off the commit HEAD pins, a dependency missing or off its pin, a record that did not build here (its log tail on stderr, the build dir kept in this checkout) or that binds another agentrc than the one staged, an agentrc file changed since this process loaded it, an input that moved while frozen, a board not in `test/hil/ci.json`, and a run id used before. It then creates the create-only attempt directory, stages and verifies the bundles and hosted builds there and launches `scripts/hil_remote_driver.py` detached: its own session, its stdio on the attempt's files, agentrc's launch and completion records in its `.attempt/`. The driver refuses (`refused`, nothing admitted) a staged bundle that does not hash as the manifest says and a `hosted/` tree that is not exactly the manifest's files with their hashes (an extra, missing, changed or linked file), rebuilds detached checkouts with no remote, worktree pointer file or link to htpc, checks each repository's commit and clean state, the pins, the roster digest and its own, moves the staged `.agentrc/` into the checkout (ignored there, so the checkout stays clean), where its bootstrap selects it for everything launched from it, and refuses on any difference, a staged agentrc that is not exactly the manifest's files with their hashes, or an unreadable CI state root, before anything loads agentrc. Then per board, one after another: CI's markers (a board with an unfinished CI battery is a blocker, not admitted; the runner checks again under its lock), the record admitted from `hosted/<board>` as CI admits its hosted build (`hil_hosted.py admit`; a refusal is not-run), and `hil_test.py run -b <board> --build-record <record> --run-root <attempt>/out/<board> --lock-wait <left> --ci-state-root <CI state root> test/hil/ci.json` through `hil_ci.py`'s `run_board()`, CI's markers read, never written. Each verdict is `hil_run_report.py`'s, and each run dir's report pair is prepared as CI prepares it, before the copy-back. `result.json` is the driver's outcome, `progress.json` its rows so far.

`--lock-wait` defaults to 0 and is one budget for all of the attempt's batteries, counted from the first one's start (at most 3600 s); a recovery blocker is never waited for. `--fail-at` is acceptance only. `install`, `restore`, `clear-pending`, `--under-hold`, `--report`, `--try-reentry`, `--route`, `--build-record`, `--run-root`, `--ci-state-root`, `--done-marker` and `--started-marker` are refused before staging. No `HIL_*` variable is forwarded, the driver drops the rig's own `HIL_*` and `GIT_*` before the rebuild, `HIL_NO_BOARD_LOCK` set here refuses the run, and a caller's `GIT_*` (a hook's `GIT_DIR`) never reaches the identity check or the bundles.

`run` waits for the attempt's completion record and collects it; `wait` reconnects and does the same within `--timeout` (at most 570 s); `collect` fetches the attempt whatever its state. Neither launches it again, and the end of `run` or `wait` (a timeout, a kill, a dropped connection) ends nothing on the rig: the attempt runs to its completion record. A launch whose acknowledgement was lost is found by its records and waited for, never launched twice.

## Reservation

Locks are taken through agentrc's `hil` helper, `skills/hil/scripts/hil_lock.py`, loaded like every agentrc script the runner, `hil_ci.py`, `hil_remote.py`, `check_build.py` and the code-size launcher use through `scripts/agentrc.py`, the bootstrap, and agentrc's `hil_load` (one module per file per process). The bootstrap selects, without running agentrc code: the staged copy when the checkout holds `.agentrc/` (a remote attempt's, Execution, Remote; any gap there is an error, never a fall-through), the commit `test/hil/agentrc.json` pins in CI (`GITHUB_ACTIONS` or `CI` true; fetched into the ignored `lib/agentrc` by `python3 .claude/skills/hil-contract/scripts/agentrc.py fetch`), else the installed `"${AGENTRC_DIR:-$HOME/.claude}"`. It checks agentrc's `agentrc_source.py` API, then takes the identity (commit, closure digests) of its `SCRIPTS`' closure once per process, and loads only a closure file whose bytes are still that identity's. `hil_test.py`'s `run`, `install` and `restore` refuse before any hardware access when no usable agentrc is selected or a script they load lacks what they call; the manual `hold`, `release` and `status` below run the helper directly, with no such check, from `<agentrc>`, the `root` that `python3 .claude/skills/hil-contract/scripts/agentrc.py check` prints (the installed agentrc's checkout, or a remote attempt's `src/.agentrc`). The lock is the board's `<lock>` (Hosts/rosters): `hold` and `release` take it and `status` (no board argument) shows it, while `hil_test.py -b` and the probe scripts take the board name.
- **The battery locks itself,** as `hil_test.py run`, through the helper's `board_task`, which the helper's `release`
  refuses to kill; agentrc's `hil` Board locks and the `BoardTask` docstring own the verdict semantics, the lock's end,
  the signal limit at `__exit__` and the one-board-per-process rule (`run` takes one board and exits). Its record is
  protected (`cleanupOwed`) and names its run dir (`runDir`). Its verdict collector (`board_task(..., verdict=)`,
  `end_board`) gives the task one verdict at its end, from the row's cleanup:

  | Verdict | When | Exit |
  |---|---|---|
  | failed | `cleanup.pass` false: a child that survived SIGKILL (logged `unrecheckable`), an `openocd_esp` session not ended (logged `retained`), a failed or injected restore; a cleanup that raised after the battery ran (logged `unrecheckable`) | 4 |
  | restored | the cleanup passed on a touched board, whatever the battery did | the battery's |
  | clean | `cleanup.state` `untouched`; a refusal after the take (an unfinished CI attempt, a live legacy session, a marker or state root it cannot use); or the battery's setup raised before any hardware access | the battery's, or the refusal's |

  A lock that did not end as its verdict said (`ended_cleanly` false) makes the exit 4 whatever the verdict; the row's
  `lock` records the end (Results). A past failure alone refuses nothing: `hil_lock.py status` shows a board's open
  failures and each run reports those it found on taking the board (`previousCleanupFailure`). Only an older tinyuf2
  runner's cleanup holder still holds a flock past its run (Recovery, Legacy).
- **The busy check.** Taking the lock is no permission to touch the probe. Under the lock, before any hardware access,
  `board_task` runs `probe_busy`: agentrc's `hil_flash.probe_users` over the board's roster flasher (`flasher_of`: its
  name and probe serial, and an `openocd` probe's roster `vid_pid`), whose docstring says what it sees and misses.
  Users refuse the run (exit 2, `probeUsers`: each `{pid, cmd}`), the lock released with no failure logged and no
  `.started` marker touched; a check that cannot decide is not run (`detail` `probe check: ...`, exit 1). It is a
  snapshot, never proof that nothing uses the board (a DUT-side tool such as `mcopy` or a serial monitor is not seen),
  so CI's `.started`/`.done` markers stay the backstop for a killed battery's leftovers (Execution, CI).
- **A remote run takes no lock of its own** (Execution, Remote): each of its batteries is `hil_test.py run` on the rig and locks its board as above, then, holding it and before any hardware access, checks CI's state root (`--ci-state-root`, Results). Attempts on different boards run side by side, one on a held board waits for `--lock-wait` (its last take may land just past it) or is not run, and an attempt id is used once. CI's markers stay CI's: a remote run never writes them.
- **The lock fails closed.** An unusable lock dir refuses the run (exit 2); it never runs unlocked. `HIL_NO_BOARD_LOCK=1` is the bypass (`hil` Board locks); the row's `lock` then says `bypassed: true` and `taken` false, the busy check still runs, a failed cleanup is logged all the same (`log_cleanup_failure`) and a restore resolves nothing.
- **Manual sessions** (hw-debugger, hw-validator):
  1. Take your own hold: `python3 <agentrc>/skills/hil/scripts/hil_lock.py hold <lock> --reason "<unique session reason>"`.
  2. Install a build record's TinyUF2, and restore the board when done:

     ```bash
     python3 .claude/skills/hil-contract/scripts/hil_test.py install -b <board> --build-record <record> --under-hold "<reason>" <roster>
     python3 .claude/skills/hil-contract/scripts/hil_test.py restore -b <board> --build-record <record> --under-hold "<reason>" <roster>
     ```

     `install` is the battery's install step from the record through the flash provider (Execution: a J-Link, ST-LINK or openocd board gets the record's HEX, an Espressif board the four IDF segments, over `--route openocd_esp` through its route), then waits for DFU; it takes the record the battery takes, admitted the same way, so it needs a clean build of HEAD. `--try-reentry <method>`, while the roster's `reentry` is unset, gives DFU's fallback (Execution, dfu) for commissioning; `restore` takes it too. `restore` is the cleanup (Execution, step 6), from a clean build record of HEAD. Each first takes the board's session mutex (`hil_lock.session_mutex`, `<lock>.session.mutex` in the lock dir), before checking your hold, so two commands under one hold never overlap, whatever tree or OS user runs them: a second is refused (exit 2) while the first runs. Both refuse unless the hold is provably yours: the record's reason, a live pid, a FLOCK on the lock file in that pid's own fds, and a failing probe of the flock. Both run the busy check (above) before any hardware access: users refuse (exit 2, `probeUsers`) and an undecided check runs nothing (exit 1, `probe check: ...`), your hold kept either way; and both refuse while a legacy pending mark lists an `openocd_esp` session still running (Recovery, Legacy). What either touched and failed, an unexpected error included, and any child that survived SIGKILL or session it left not ended, is appended to the board's cleanup log through the helper's `log_cleanup_failure`, which never ends your hold; a `restore` that passed marks restored each open failure its evidence resolves.
  3. Release with `python3 <agentrc>/skills/hil/scripts/hil_lock.py release <lock>`, only after a `restore` that exited 0 with no `survivors`. Otherwise the board is not cleaned up, its failure logged: keep the hold and report it as a blocker.

  Manual exits: 0 the operation succeeded (for `install`, DFU came up; for `restore`, DFU left after the blinky copy and stayed away); 1 it failed before writing; 2 refused before any hardware access; 4 a child survived SIGKILL or an `openocd_esp` session is not ended (cleanup pending), each in `survivors`, or an `install` or `restore` failed after it began writing, logged in the board's cleanup log (`failureLogged`; `logError` when it could not be): keep the hold. `buildLocksKept` names a build dir whose lock a keeper holds until the listed survivors end.

  On a refused hold, `python3 <agentrc>/skills/hil/scripts/hil_lock.py status` (no board argument; it prints every
  holder and each board's latest open cleanup failure) gives the holder to report. A `role: cleanup-holder` holder is an
  older tinyuf2 runner's (Recovery, Legacy); any other live `hil_test.py` holder is a battery run (`hil` Board locks:
  wait within the budget). A `stale` record (a task that ended without its cleanup) or an older helper's
  `takeover journal` refuses nothing: the next task takes the board and logs it. An
  `acquisition in progress or interrupted` line is neither a holder nor a blocker: a taker is writing its first record,
  or died doing so, and the board is free once that taker is gone.
- **Cleanup state** for a hw-validator or hw-debugger dispatch: `restore --under-hold` leaves the board on the record's TinyUF2 with `apps/blinky` copied through it, and its `cleanup.evidence` (DFU left after the copy and stayed away) is the observation that Cleanup records. Blinky running is not checked. Whoever uses the board next flashes it first; tinyusb's HIL does.
- **Lock-wait budget:** htpc has no CI runner, so it is the dev-bench row of chief's budget unless the dispatch names another; ci.lan is the CI-runner row. `run --lock-wait <s>` keeps trying a held board that long, plus one last take once its final pause ends, never an older runner's cleanup holder (a recovery blocker), and a SIGINT or SIGTERM ends the wait at once as a `locked` row; the CI job passes its own (Execution, CI).

## Results

The last stdout line is JSON. It is also published, through agentrc's report core (`hil` Reporting; `scripts/hil_run_report.py` is this runner's adapter), as the run directory's `hil_report.json`, `reportPath`: the same fields plus the reserved `_hil` (attempt id = the run directory's name, termination `completed` or `aborted` by a signal, invocation, the board, host, the roster's file name and sha256 (the same in a checkout and on a rig), and the admitted record's `firmware` as build provenance, omitted when none was admitted), with `hil_report.md` beside it, a view of each board's steps rendered from that JSON. A report the core could not publish adds `reportError` to the stdout JSON, and `reportPath` is `null` unless its JSON was written; the run's exit and row are unchanged. Its fields:
- `pass`, `caveat` and `exitCode` (the runner's exit), from which the Verdicts below follow from the file alone (an older runner's report may carry `heldInProcess`: that runner stayed the cleanup holder, so its exit is unknown and its row a blocker);
- per board: `ran`, `pass`, `locked`, `recoveryBlocker` (a `locked` row whose holder is an older tinyuf2 runner's cleanup holder, Recovery, Legacy; or, with `run --ci-state-root <dir>`, a transition check a driver passes CI's state directory for, an `unfinishedAttempts` row: a CI run under it started a battery on the board and has no `.done`, its liveness never guessed, and this run is refused after its own lock and before any hardware access, its lock released with nothing logged; an unreadable state directory refuses, exit 2), `lock` (the board lock's `name` and its task's end, agentrc's `BoardTask.report()`: `taken`, `released`, `bypassed`, `ended`, `endedCleanly`, `failureLogged` (null when the end logged no failure), `errors`, `describe` (the task's one line on its end, display text) and `restoreNotes`, why an earlier failure stays open after a restore or its restoration was not logged; decisions read the exit and these booleans, never the text), `previousCleanupFailure` (the latest open failure in the board's cleanup log as this run took the board, the helper's `failure_report`) and `openCleanupFailures` (how many are open, when more than one), the refusals of live work (Reservation; exit 2): `probeUsers` (each `{pid, cmd}` the busy check named) and `pendingSessions` (a legacy mark's session still running), `legacyPending` and `legacyNote` (an older runner's pending mark: Recovery, Legacy), all shown under the board in `hil_report.md` as `Notes:` with each of `lock.restoreNotes` and `lock.describe` when the lock did not end cleanly, logged a failure, was bypassed or met errors, or an older runner's cleanup holder still holding the board (Recovery, Legacy) (a manual report's `restoredNote` and `logError`, why its failure was not logged, at its top), never changing a verdict, `firmware` (path, sha256, version, build record), `steps[]` (`step`, `pass`, `evidence`, `detail`), `cleanup` (`pass`, `state`, `evidence`, `detail`, `survivors` (children that outlived SIGKILL, each by pid and start time, and sessions not ended), and `receipts` when `state` is `pending`; an older runner's report may carry `heldAfter` and `holder`, Recovery, Legacy), `jlinkRetried` (J-Link boards only: sessions run again after a crash before the target connect, each `{exit, commands}`; Limits), `route` (a run over a `tinyuf2.routes` route), `buildLocksKept` (each `{buildDir, survivors, keeper}`: a build dir whose lock a keeper holds until those children end), and `detail`;
- `update` (the update battery's: Execution, Update);
- in an install's evidence (`steps[0]`, `cleanup.evidence`, a manual `install`): `operation`, the provider's record of the flash, `{attempts: [{kind, exit}], cleanup, receipts}`, each attempt's `kind` `exited`, `timed_out`, `interrupted` or `error` and the operation's `cleanup` `done`, `pending` or `unknown` (`hil` Flashers), never the transcripts joined (they are in the run dir's `hil.log`); on an Espressif board also `esptool` (its version), and on the `openocd_esp` route `route`, `security` (the evidence passed to the provider) and `jtag` (openocd build, USJ bus-port, session log). A failed flash's step evidence carries `operation` and `beforeTarget`;
- `cleanup.state` is `blinky copied`, `untouched`, `unknown` (touched, not restored), or `pending`: an `openocd_esp` session is not ended (Recovery, Cleanup pending), its receipt in `receipts` and in `survivors` (`{cmd, receipt}`, with `pid` and `start` when the receipt was readable; `receipt` is the provider's record itself when it could not be written) and in the logged failure's `retained`, the board released and the build lock kept by a keeper;
- `error` on a refusal or an operation failure.

| Exit | Meaning |
|---|---|
| 0 | every board passed and was cleaned up |
| 1 | a board failed or did not run; it was cleaned up or never touched |
| 2 | refused before any hardware access (usage, roster, source, build record, lock helper, lock dir) |
| 4 | cleanup failed or is pending, or the lock did not end as its verdict said (Reservation); the board released (`lock.released`, unless its flock did not close or under `HIL_NO_BOARD_LOCK`) and the failure logged in its cleanup log (`lock.failureLogged`), or `lock.describe` says why not. From `install` or `restore`: a child that survived SIGKILL or an `openocd_esp` session not ended, or the operation failed after it began writing, logged as a failure; keep your hold |

A delegated run (`hil-operator`) returns `{pass, results, caveat, wedged}` and, beside them, `reportPaths`:
- `reportPaths` maps each board to its JSON's `reportPath` (`null` with `reportError` when it was not published), which a recovery dispatch needs.
- Across several boards (Execution: one battery per board), `results` holds every board's row, `pass` is true only when every run's is, and `caveat` joins the runs' non-empty caveats.
- A launched run that ended without printing its JSON (killed, crashed) may have programmed the board and left it running a candidate. The operator writes `pass: false`, `caveat: "run ended without a report; board state unknown"` and one row per board, exactly `{board, ran: null, pass: false, locked: false, detail}`, with `detail` naming the exit status, the output tail and `python3 <agentrc>/skills/hil/scripts/hil_lock.py status` at that moment.
- The operator runs the battery once and returns. It never waits on a lock and never retries: a `locked` row comes back as is, and its caller retries under `hil`'s Caller rules, marking a flaky pass `flaky: true`.
- A recovery dispatch runs Recovery's `restore --under-hold` under its own hold, with `--report` when the failed run printed one, in the foreground and returns `{pass, results, caveat: "", wedged, exit, error, survivors}`: that JSON's `results`, `error` (`null` when absent) and `survivors` (`[]` when absent), and the exit status. Any exit but 0 is a blocker for the caller. A probe that cannot connect is `needs-user` (the board's recovery note, Recovery).

### Remote results

`hil_remote.py` (Execution, Remote) prints one JSON line, also kept as `.hil-remote/<run id>.outcome.json`: `outcome` (`pass`, `fail`, `blocker`, `refused`, `incomplete`, or for an attempt not done `running`, `dead`, `not-launched`, `inconclusive`), `pass`, `collection` and `remoteState`, `remote` (`host`, the attempt's `dir` and `checkout` on the rig, and `local`), and per board `phase` (`preflight`, `build`, `battery` or `driver`), `verdict` and `detail` (Verdicts; a refused admission is `not-run`, phase `build`), `exit`, `previousCleanupFailure`, `openCleanupFailures` and `notes` (as CI's), `reportError`, `unfinishedAttempts`, `heldInProcess` and `holder` (only from an older driver's attempt), `sharedVerdict` and `sharedDetail` (as CI's, never the exit), `unsafeArtifacts` (views the rig could neither prepare nor withhold: removed from the local copy, never evidence, as is every view of a collection without a readable `result.json` and of a board whose row has no prepared report pair), and `paths`: `buildRecord`, `runRoot` and each run dir's `reports`, every one as `{remote, local}`; `driverFailure` when the driver itself failed or exited other than its rows say, which makes the outcome a blocker whatever the rows. The attempt comes home into `.hil-remote/<run id>/`: `manifest.json`, `result.json`, `progress.json`, `out/` (each board's record and run root: `stdout.txt`, `stderr.txt` and the run dir with its report pair and `hil.log`), `.attempt/` (agentrc's launch and completion records and the driver's stdout and stderr) and agentrc's `collection.json`. Only the attempt's own paths are fetched, never one a report names. A file the driver's inventory lists, or the board's phase requires (a battery's record, `stdout.txt`, `stderr.txt` and its published `hil_report.json`), that did not come home makes the board's `copyBack` `incomplete` and the outcome `incomplete`, even after a pass, the board's own verdict kept; a later `collect` fetches such an attempt again and keeps the new copy only once it is whole. Evidence collected before the attempt is done is `incomplete`, never a pass, and never replaces a complete collection.

| Exit | Meaning |
|---|---|
| 0 | every board passed and came home whole |
| 1 | a board failed or was not run, a refused admission included |
| 2 | a blocker: failed cleanup, a run without a report, a recovery blocker (an older runner's cleanup holder), a process on the board's probe or a legacy session still running, an unfinished CI attempt |
| 3 | still running at `--timeout`; wait or collect again |
| 4 | the attempt ended without its completion record (`dead`), or was never launched |
| 5 | inconclusive: the rig unreachable or its evidence incomplete, a transport failure after the launch included |
| 6 | incomplete copy-back |
| 7 | refused: here before staging (a record that did not build here included), or on the rig before any admission (`refused`); `error:` on stderr says why |

### Verdicts

Each board's row maps onto the `hil` verdicts, except a commissioning run's (`commissioning: true`, from `--try-reentry`), which is never validation.
- `pass`: `ran`, `pass` and `cleanup.pass` all true;
- `fail`: `ran` and not `pass`, with a failing step, `cleanup.state` other than `untouched`, and that step's `detail`;
- `not-run`: `ran` false (`locked`, a refusal, or a probe check that could not decide: not exactly one tty with the route's serial, a process it could not read), or a failing step with `cleanup.state` `untouched`, with its `detail`. Nothing was written, so the failure is the rig's: no probe with that serial on this machine, or one unplugged or dead;
- a blocker, never a `fail` row: exit 4, `ran: null` (no report), a `recoveryBlocker` row, a `probeUsers` or `pendingSessions` row, and an abort, which is `ran` and not `pass` with no failing step (an interruption or an unexpected error, named in the board's `detail`).

An open cleanup failure a run found (`previousCleanupFailure`) is reported beside its verdict and never changes it.

`testedHead` is the build record's `input.head`. `regression` is `unknown` unless the battery also ran on the merge base.

## Recovery

A lock ends with its run (Reservation): recovery never releases or takes over a holder. It restores the board under a
hold of its own, and a restore that passes resolves the failures the board's cleanup log keeps open.

- A board whose run ended without a report gets a manual `restore --under-hold` (the recovery dispatch below, as for
  exit 4) before its next run, and only once no such process is left on the host. The dead battery's record stays on
  the free flock until the next taker, the dispatch's own hold included, logs it as a `found-left` failure. Killing the
  runner frees its lock but not its children: the next run's busy check sees only a process on the probe, and a child
  on the board's USB devices is tied to nothing, so the check is host-wide: any other battery, J-Link or openocd
  session also keeps the blocker. Run this as a command of its own, since a shell line
  carrying the plain name would match itself; none is left when it prints nothing:

  `pgrep -ax JLinkExe; pgrep -ax openocd; pgrep -ax mcopy; pgrep -af '[h]il_test\.py'; pgrep -af '[e]sptool_session\.py'; pgrep -af '[u]sb_dfu\.py'`

  The `hil_test.py` check also covers the runner's `fat-read`, `flush` and `uf2-write` subcommands. While a process is left, or this cannot be established, the blocker stays.

Exit 4, a failed cleanup:

- The run's lock ended with it (`end_failed`): the board is released, and its cleanup log holds a `failed` event with
  the run's record, `detail`, its children that survived SIGKILL as `unrecheckable` `receipts` (by command and pid:
  nothing can recheck them, so no later restore resolves that failure, which stays open for the lead or the human) and
  the `openocd_esp` sessions it `retained`; `lock.failureLogged` is false when the append failed, and `lock.describe`
  says why, or what other part of the lock's end failed.
  `hil_lock.py status` shows it, and the next run on the board, of any project, reports it (Results) without being
  refused by it alone. A CI battery's failed cleanup also leaves its marker (Execution, CI).
- `cleanup.survivors` lists children that outlived SIGKILL (a J-Link, mtools or FAT read stuck on the device), each by
  pid and start time, and any `openocd_esp` session not ended (cleanup pending), with its receipt. A recovery `restore`
  refuses no survivor by itself: its busy check sees one on the probe, and the host-wide check above the rest. A
  session's receipt is reread on every check, never remembered.
- Cleanup pending: the runner never signals an openocd-esp32 server (a killed one can leave the chip in its Breakpoint boot loop), so a pending receipt is the lead's to resolve, never the recovery dispatch's. The dispatch reports the receipt and stops. A session's state, read from its receipt on every check, is `ended` (closed with cleanup `done` by the provider's end), `running` (open, a process with its pid and start time, a zombie included, or one whose `/proc` entry cannot be read), `unreadable` (also while the provider cannot be loaded), or `unresolved` (closed without that end, or its process gone without closing it), as the provider's `session_state` reads it. The build lock's keeper exits once none is `running` or `unreadable`; everything else waits for `ended`. The lead runs `python3 <agentrc>/skills/hil/scripts/hil_openocd_esp.py end --receipt <receipt> [--timeout S]`, which ends the session only after proving its last command ran and its init was `ok`, by `reset run` then `shutdown`; never SIGTERM or SIGKILL the server. Exit 0 (`ended` or `alreadyEnded`) leaves the receipt closed with cleanup `done`, which discharges it from `survivors` and the keeper; then the recovery `restore` below runs, with the route's `--route`, and resolves the logged failure, or, after a manual `install`, `restore --under-hold` and `hil_lock.py release` (Manual use). Exit 1 (refused or failed) keeps the receipt and the failure open; 2 is a usage error. A receipt whose init failed or is unproven, one closed without the reviewed end, one whose process is gone without closing it, and a session whose receipt the provider could not write (a record with no path in `survivors`) need a separately reviewed recovery, the lead's or the human's to decide; none is defined here.
- An open failure may stand for a stuck J-Link or mtools process; tinyusb's reflash does not make
  the board safe, so report the board until a restore resolves it.
- Recovery is a separate `hil-operator` dispatch under `hil`'s Board locks scope, carrying the board, the failed run's
  `reportPath` and a record. After process, probe and host readiness are established, it takes its own hold
  (Reservation, Manual sessions), runs

    `python3 .claude/skills/hil-contract/scripts/hil_test.py restore -b <board> --build-record <record> --under-hold "<recovery reason>" [--report <reportPath>] <roster>`

  and releases its hold only after a restore that exited 0 with no `survivors`. `<record>` is the failed report's
  `firmware.buildRecord`, or a record rebuilt on the clean HEAD when it no longer verifies (on ci.lan, built off the rig
  and admitted there: Build, Hosted). `--report` is read through the report core before any probe: a report without
  `_hil` (an earlier runner's) is read as it is, one that is missing or corrupt or carries an unknown `_hil` or body
  version is refused (exit 2), and its rows of this board must hold exactly one whose cleanup failed or whose lock did
  not end cleanly (`lock.endedCleanly` false: exit 4 either way). On an Espressif
  board the restore checks the preserved regions against that row's snapshot, refused for a touched run without one or
  one whose regions differ from the checkout's; without `--report` (a run that printed none) it takes a fresh snapshot,
  so the preserved regions are proven unchanged only across the recovery itself, never across the failed run, and the
  dispatch reports that limit with the board. A restore that passed marks restored each open failure whose own evidence
  resolves; a refusal (exit 2) or a failed restore (exit 4, its failure logged) leaves them open: keep the hold and
  report the blocker, and missing recovery evidence stays a blocker for the lead or the human. A candidate whose drive
  cannot take the blinky copy fails the restore; the board stays a blocker until a record that can restore it is given.
  A second `install` or `restore` under the hold while one runs is refused (exit 2, its session mutex).
- A CI battery runs as `ghrunner-tinyuf2`: the ssh user's busy check reads its command lines but not its descriptors,
  so a probe tool of that user refuses or leaves the check undecided (Reservation); a recovery that must read them runs
  as that user (`sudo -u ghrunner-tinyuf2 ...`) or as root.
- A remote attempt's board (Execution, Remote) is recovered by the same dispatch, run on ci.lan from the attempt, never
  through `hil_remote.py`: in the outcome's `remote.checkout`, with `paths.buildRecord.remote` as `<record>`, a
  `paths.reports[].remote` as `<reportPath>` and `test/hil/ci.json` as `<roster>`. A later run never wipes an attempt;
  one is removed by hand only once its collection is complete and none of its boards is a blocker.
- If the probe cannot connect, recovery is the human's: on imxrt1060_evk, serial download mode (BOOT_MODE 01: SW7 OFF OFF OFF ON, inferred from the EVK guide), and on imxrt1064_evk the same switch (SW7, MIMXRT1064-EVK schematic sheet 16), on the ci.lan rig, where tinyusb's roster also gives the board an OpenOCD recovery flasher; on espressif_esp32s3_devkitc_1, ROM download mode: hold Boot (SW1, GPIO0 low), press and release RST (SW2, CHIP_PU), then release Boot (DevKitC-1 schematic V1.0; the TRM's strap table also needs GPIO46 low, its default pull-down); on espressif_p4_function_ev, the same with BOOT (SW2, GPIO35 low) and RST (SW1, CHIP_PU) (Function-EV-Board schematic rev 1.4); on stm32h563_nucleo, a power cycle: unplug and replug its STLINK USB (CN1), which powers the board (bench-history.md); on metro_m7_1011, serial download mode: DIP switch SW2 position 1 ON (BOOT_MODE0 to 3.3 V through R17) and position 2 OFF (BOOT_MODE1 left to the pin's default pull, unchecked), then press RESET, which drives POR_B, on whose rising edge BOOT_MODE is latched (Metro M7 RT1011 SD rev A schematic: SW2, R14, R17, RESET; IMXRT1010RM Rev 0, 9.3.1, p. 157, BOOT_MODE 01b the serial downloader). The ROM's SDP device (1fc9:0145, `ports/mimxrt10xx/family.cmake` `SDP_MIMXRT1011_PID`) then takes TinyUF2 into RAM with `cmake --build <record's buildDir> --target tinyuf2-sdp` (`sdphost` on the host), and TinyUF2 started in that mode writes itself to flash (`board_flash.c` `board_flash_init`); set SW2 back (internal boot, BOOT_MODE 10b: position 1 OFF, 2 ON) and press RESET. That route is unverified on the bench.

Legacy, from before task-scoped locks:

- An older tinyuf2 runner's cleanup holder (`role: cleanup-holder`, its flock still held: a `locked` `recoveryBlocker`
  row, never waited for), its in-process holder (`heldInProcess`, `cleanup.holder.inProcess`) and its takeover journal
  are recovered only with a tinyuf2 checkout matching the runner that made them together with agentrc bf7f009, the
  commit that runner pins, under a recovery dispatch naming the board and the holder: that checkout's
  `restore --recover-holder` or `--recover-takeover`, as its own contract says. The current helper's
  `hil_lock.py release --token` cannot release them, since tinyuf2's old holder records carry no token; never run it, or
  kill the holder, by hand. A record or journal such a holder left on a free flock is logged by the next taker like any
  other leftover.
- Reports and remote outcomes from those runners may carry `heldInProcess`, `cleanup.heldAfter` and `cleanup.holder`:
  their readers take them as that holder's, never as a released board.
- A pending mark, `<lock>.tinyuf2-openocd-pending.json` (`hil_lock.PendingSessions(<lock>, "tinyuf2-openocd")`), is an
  older runner's record of `openocd_esp` sessions not ended; no runner writes one any more. A `run`, `install` or
  `restore` that meets one reports the sessions not proven ended (`legacyPending`) and logs them once in the cleanup log
  as retained, which a restore resolves only once each reads `ended`; one still `running` refuses (exit 2) as live work
  does, and the mark is removed once every listed receipt reads `ended`. Removing it never marks a cleanup-log failure
  restored. `clear-pending` is legacy maintenance: `clear-pending -b <board> <roster>` removes the mark only when every
  listed receipt reads `ended`, and otherwise refuses naming them (exit 2), with no hold needed; after a separately
  reviewed recovery that ended the sessions some other way,
  `clear-pending -b <board> --after-reviewed-recovery "<note>" --under-hold "<reason>" <roster>` proves your manual hold
  under the board's session mutex as `restore` does, appends the note, the hold's record and the mark's content to
  `<mark>.cleared.jsonl` and removes the mark (exit 0). Never remove the mark any other way.

## Limits

Measurements and dated bench observations behind these limits, loader footprints included, live in `bench-history.md` beside this page.

- Covered: imxrt1064_evk, lpcxpresso55s69, stm32f407disco, stm32h743nucleo, max32666fthr, espressif_esp32s3_devkitm_1, espressif_p4_function_ev, metro_m4_express and ch32v407_r0 on ci.lan, all but imxrt1064_evk, metro_m4_express and ch32v407_r0 commissioned on 2026-10-22, metro_m4_express on 2026-11-01 and ch32v407_r0 on 2026-11-12 (bench-history.md); max32666fthr was commissioned on its earlier openocd probe and is pending commissioning on its J-Link: `test/hil/ci.json` sets no `reentry` for it, so CI only builds it on a dispatch (below). htpc covers only what its untracked roster lists while those boards are attached; imxrt1060_evk, metro_m7_1011, stm32f303disco, stm32f411ve_discovery, stm32h563_nucleo, espressif_esp32s3_devkitc_1, espressif_p4_function_ev and espressif_esp32s31_func_core were commissioned there (bench-history.md). Not covered: devices without flash limits in the runner (`FLASH_LIMITS`), non-Arm ports other than ch32v4x7 (the fixture is a Cortex-M image, or an RV32 one for ch32v4x7: ch32v20x is refused), stm32h7 boards other than an internal-flash app's (the H750 boards are refused: their app, in QSPI flash or AXI SRAM, starts outside internal flash), espressif chips other than the ESP32-S3, ESP32-P4 and ESP32-S31, self-update and an interrupted update outside the update battery (Execution, Update: J-Link boards of mimxrt10xx only; every other port's updater is a self_update app, ST-LINK and Espressif boards included, and ports kinetis_k32l2, stm32h7, stm32l4, ch32v20x and ch32v4x7 build none), malformed UF2 input, the physical double tap, and TinyUF2's write protection on the STM32 boards: a battery runs F303 unprotected after any option-byte reload until a power-on reset, leaves F411's and F407's protection set, and the H5 sets none today; on the H5 the runner never removes protection and an install that meets it fails.
- On ci.lan, imxrt1064_evk's probe (1-1.1) and its USB (1-1.2) share one hub, the farm's cabling, where commissioning.md asks for separate hubs: a device hung mid-write there could stall the probe connect too (Shared hubs below). Its silicon revision was not read from the marking (the rig is remote); the A and B errata were both checked. Whether its FlexSPI configuration observes ERR011377 (a delay after the DLL lock before the first flash access, IMXRT1064CE_A Rev 1.3 and IMXRT1064CE_B Rev 1.1) is unchecked: pending, not a found defect. Every install leaves [0x7000C000, 0x70010000) erased, an inference from one sample (bench-history.md, imxrt1064_evk), as on the RT1060 boards.
- On ci.lan, ch32v407_r0's probe (21-1.3) and its USB (21-1.1) share hub 21-1 with three other WCH-LinkEs, the farm's cabling, with the same exposure as imxrt1064_evk's above.
- The `usbPower` port cycle (Hosts/rosters) runs under the board's own lock, a limitation of `hil`'s rig-wide rule, not an exemption. On the Port Authority hub (5-3) a cycle re-enumerated only its own port's device when measured; neither a VBUS drop nor an enumeration storm was measured (bench-history.md: Shared hubs). On a ganged hub (5-1, 5-2) a port cycle removes no power while another port in the gang is powered, and can power the whole gang off when it is the last, so `usbPower` must not name a port there. On the Port Authority hub's USB2514B a full- or low-speed device that detaches and re-attaches within 100 µs of SE0 may not register as a detach (USB251xB errata, module 4); stm32f303disco's missing disconnect is instead its board's fixed D+ pull-up, by design (bench-history.md: stm32f303disco). Never cycle a rig hub port with `uhubctl` or a raw hub request: a cycle that met an enumeration in progress killed an xHCI controller. Another board's enumeration errors on the same hub can reset a neighbour mid-read, and `install`'s FAT read then times out (exit 4) (bench-history.md: stm32h563_nucleo). A device hung mid-write stalled a J-Link connect on the same hub.
- Espressif boards: the runner runs the `esptool` first on PATH, whatever its version: a console script whose absolute python shebang names the interpreter the runner also runs its esptool sessions under (the provider's `tool_python`), checked once per run, its version recorded in the install's evidence (`esptool`, `esptoolPath`) and the security reading's source. The batteries were benched with 5.3.1; the ESP32-S31 needs it, as 5.2.0 cannot reach its flash over the USJ. Install another version as a versioned venv, never over a host's own esptool, which other sessions and projects use: `python3 -m venv ~/tmp/esptool-5.3.1-venv && ~/tmp/esptool-5.3.1-venv/bin/pip install esptool==5.3.1 'bitstring<5'`, then run with `PATH=~/tmp/esptool-5.3.1-venv/bin:$PATH` (`bitstring<5`: 5.0.0 removed `BitStream`, which 5.3.1's espefuse imports). That puts the venv's `python3` first too, while the runner needs pyusb with libusb-1.0 for its own Python (`usb_dfu.py`): run it with the host's interpreter by path (`/usr/bin/python3 .claude/skills/hil-contract/scripts/hil_test.py ...`), or add pyusb to the venv. The install runs that esptool in the provider's dialect (`default_reset`, `write_flash`, flash_args inline), not the build's flash target, with `--no-stub` exactly where the build's sdkconfig disables the flasher stub, as that target does. On ci.lan both chips reach the host through a TS3USB30 mux whose select pin is GPIO47, which TinyUF2 leaves floating; the datasheet leaves that position undefined and the rig held the host side in every run (bench-history.md: esptool boards). Re-entry by DFU_DETACH is the only method built; the GPIO0 detection window is not. `--no-stub` applies to the install's flash only, which then writes uncompressed (the install's judge takes either form, every segment still hash-verified and the chip reset): the read and MD5 sessions (agentrc's `esptool_session.py`) load the stub themselves whatever the build's sdkconfig says. Over a USJ the runner opens no tty of its own, only its esptool sessions do, and it never makes a download-boot request over TinyUF2's OTG side; why, and how esptool resets each chip there, is in bench-history.md (esptool USJ resets). The route's tty carries every esptool session. A helper that survives SIGKILL is handled like a stuck J-Link, but no way to wedge one on the board was found, so that path is unit-tested only. The host log shows a USB reset and block-device read errors at the end of a UF2 copy, and on the P4 a full-speed device that never answers while an esptool session holds the chip; the battery passed with the latter.
- The copy flushes only its own drive (the runner's `flush` subcommand, an fsync of that block device node, as coreutils `sync <dev>` does it), so another drive's hung writeback (a stalled `lpcxpresso55s69` copy's, #552) does not fail it; a flush that outlives SIGKILL on its own drive still fails the cleanup, logged with it as a survivor (Recovery). TinyUF2 resets within milliseconds of the last write, so the flush's open often finds the device gone (on the P4 every time, bench-observed): an open failing with ENOENT or ENXIO after mcopy succeeded passes once DFU has left, recorded as `flush` evidence ("device disappeared before flush"). An accidental disconnect looks the same, so that copy's writeback is unconfirmed: a battery's later steps read its image back, but nothing reads the restored blinky back, so a restore then stands unverified. Any other flush failure fails the copy, a restore's included, which fails the cleanup (exit 4).
- Remote runs (Execution, Remote): the dev PC builds every record, so it needs `cmake`, `ninja` and CI's compiler release for each board's port on PATH (another release's record is refused at the build, before staging), and docker with CI's ESP-IDF image for an Espressif board; the Windows client is pending; attempts are never pruned (each holds the bundles, the hosted builds, the rebuilt checkout and the admitted build dirs). The detached attempt outliving a real ssh session and the wrapper, and the imxrt1064_evk run on ci.lan, are tested only against a local stand-in rig until a hardware run. Older CI drivers of other projects gain no awareness of tinyuf2's CI markers.
- Every probe and USB path is unverified until commissioning has run on the board, and commissioning is manual.
- The hosted route (Build, Hosted) is unverified in CI until a workflow run: on htpc (2026-10-21) `build` packed espressif_esp32s3_devkitm_1 in espressif/idf:v6.1 and `admit` placed it, and the runner's record check (`verify_record`, segments against the candidate's partition table) passed on it; for cmake boards only `build` and `admit` on htpc have run; the workflow's jobs, a remote run's staged admission and the rig's admission under the new runner user have not.
- cmake builds pass `TUF2_LOG=0` unless `LOG` is set, so the HIL image does not log on the board UART.
- `install` from a blank board, or one whose ROM found no boot image, brings up DFU on imxrt1060_evk and metro_m7_1011; until a `loadbin` has run, a new J-Link session reads such a board's flash wrong.
- That every install on the RT boards leaves the app start erased is an inference from samples, not a measurement of every image.
- The runner runs no CMake flash target: the provider runs the commands the record's targets run, with the same files, so the targets' own execution is no longer covered end to end; the record still checks each target's command against the roster at the build, and a test keeps the provider's J-Link script equal to the target's. Of the J-Link and ST-LINK boards, imxrt1060_evk, stm32f303disco and stm32f411ve_discovery are not covered by a hardware run of this direct install. agentrc's pyOCD backend is unproven on hardware and no roster board uses it.
- `openocd_esp`: never convoy-safe (`hil` Flashers), so another 303a:1001 on the host may be opened on a transfer error. openocd itself never detects flash encryption or secure boot: the runner's esptool reads them, and the chip revision's eFuse layout is from the P4 TRMs for revisions v1.3 and v3.x (the bench P4 is v1.0). The route writes the built bytes without esptool's header rewrite. espressif_p4_function_ev's route was commissioned on 2026-10-20 (bench-history.md).
- Never use the erase targets on a rig board (`tinyuf2-erase-external-jlink` erases [FLASH_BASE, FLASH_BASE + 64 KiB), the bootloader with it), nor ESP-IDF's `combined-flash`, which has no port selection and writes nvs and both OTA slots blank.
- stm32f411ve and stm32f407vg: runner sessions connect as `Cortex-M4` because a `-device` connect as the chip resets it and drops DFU, and the install's verify session waits 1 s before its halt (`JLINK_CONNECT_UNLOCKS`).
- Double-tap retention: on stm32h563_nucleo the word survives a system reset only with option SRAM1_3_RST=1 (set on this chip); on stm32f303disco, stm32f411ve_discovery and stm32f407disco its survival across SYSRESETREQ is undocumented and inferred from commissioning; on stm32h743nucleo the word is in DTCM, whose retention over a system reset RM0433 Rev 8 does not state as searched, and it survived the CLI's software reset (bench-history.md); on max32666fthr the UG keeps RAM over a system reset (MAX32665/MAX32666 UG rev 3, 4.3.3) but does not say what SYSRESETREQ maps to, so its survival is the bench's (bench-history.md), observed through openocd and unchecked through its J-Link until that battery's commissioning, and the MAX32665 datasheet and errata are not in the library.

- stm32f303disco signals no disconnect when TinyUF2 comes up after a reset, so `stays_away` (the control trial's, the copy's) and `observe_app` cannot see a transient DFU entry there; its roster `usbPower` covers DFU (Hosts/rosters).
- stm32h563_nucleo: STM32CubeProgrammer behaviour the runner relies on is bench-observed on v2.23.0 only (UM2237 not in the library).
- A `JLinkExe` crash in the install is not retried (the crash retry below covers the runner's own sessions only): it fails the install, touched unless it is the crash at the probe connect below.
- `JLinkExe` sometimes crashes in `libjlinkarm` at the probe connect on htpc, cause unknown. A session that crashed this way, before the target connect, runs once more after 2 s through the provider's `run_jlink_commands` `retry_if` (`jlinkRetried`), which refuses the rerun unless nothing of the crashed session's process group was left (the step's `retryRefused`); a second crash fails the run.
- The update battery is hardware-pending until its first bench run (metro_m7_1011 first): its copy, readback, interrupt and recovery paths are unit-tested only. Whether its reset overlaps the write depends on the probe session's start-up time against the passes' erase and program time, measured by no run yet; each run reports it (`writeInFlight`), and a run without it fails; what a first run did not observe is in bench-history.md (Update battery). What the RT1011 and its external NOR flash do on a reset mid-erase is not established: the flash's datasheet (W25Q64JV, the Metro M7's) is not in the reference library, and the RT1010 manual and errata (IMXRT1010CE Rev 1) say nothing of a reset during a FlexSPI NOR erase. Recovery relies on the probe's install, which brought DFU up from a board whose ROM found no boot image (RT boards, bench-history.md), and on the human fallback in Recovery.
