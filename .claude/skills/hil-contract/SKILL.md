# HIL contract

`scripts/hil_test.py` holds the mechanics: roster and source checks, firmware binding, locking, the probe and USB steps, cleanup and the JSON report. Agents call it instead of composing J-Link, mtools or lock commands. This page is TinyUF2's contract under agentrc's `hil` skill, which is read first.

## Hosts/rosters

- One roster per host, `<roster>` in the commands below: `test/hil/local.json` on htpc's bench and `test/hil/ci.json` on the ci.lan rig (`hostname` `ci`, where the CI job below runs); `hostname` says which you are on. Elsewhere a J-Link or ST-LINK run fails at `install`, where no probe with the roster's serial is found, before anything is written: `cleanup.state` is `untouched` and nothing stays held. An esptool board without exactly one bridge tty with the roster's serial stops at the runner's probe check, after the lock: a `ran: false` row with `detail` `probe check: ...`, nothing written and nothing held. Both hosts are shared with tinyusb's rosters (its contract's Hosts/rosters: `test/hil/local.json` on htpc, `test/hil/tinyusb.json` on ci.lan): a rig-wide operation holds both rosters' lock names (`hil` Board locks), tinyusb's under the names and in the sequence its contract's Reservation gives.

A roster entry is named by its TinyUF2 board (`ports/<port>/boards/<name>`, which also gives the port) and keeps tinyusb's shape (`name`, `uid`, `flasher {name, uid, args}`), so agentrc's `rtt.py`, `pc_sample.py` and `probe_state.py` resolve the probe with `--hil-config test/hil/local.json --board <name>`. A J-Link entry has `args` exactly `-device <name>`; the runner uses SWD at 4000 kHz, so pass the same to those scripts, `--interface swd --speed 4000`. An ST-LINK entry has `flasher.name` `stlink`, `flasher.uid` the ST-LINK's USB serial and `args` exactly `-device <name>`, a name the runner holds limits and a chip identity for (`FLASH_LIMITS`, `STLINK_CHIPS`); STM32CubeProgrammer takes no device name, so every session checks the Device ID and NVM size it prints. An espressif entry has `flasher.name` `esptool`, `flasher.uid` the USB-UART bridge's serial (`/dev/serial/by-id/*_<flasher.uid>-if*`), `flasher.args` exactly `--chip <chip>`, and the top-level `uid` the chip's factory MAC, which is TinyUF2's USB serial. The roster holds the board's hardware only; layouts come from the candidate's source. The `tinyuf2` block holds:
- the board lock name (`lock`) when tinyusb names the board differently, as `mimxrt1060_evk` for `imxrt1060_evk`; both runners take that one lock, and the helper's `status`, holder records and the report rows' `lock` show it. It defaults to the board name;
- the commissioned re-entry path (`reentry`);
- for a board whose TinyUF2 signals no disconnect when it comes up after a reset, the per-port-power hub port its USB is on (`usbPower`: `{"hub": "<hub USB serial>", "port": N}`; the serial, not the bus location, so a replugged hub is still found). J-Link boards only. The hub must switch that port's power on its own. `uhubctl` showing `ppps` is a required preliminary check, not proof: a hub with several gangs, or with no power switches, may report per-port switching too (USB 2.0 11.11, 11.11.1). On a ganged hub a cycle removes no power while another port in the gang is powered, and can power the whole gang off when it is the last (USB 2.0 11.11). The board-only lock is relied on only once commissioning has shown VBUS on that port drop and the cycle reach no other port (commissioning.md, Port power). While `dfu` waits, the runner power-cycles that port, under the board's own lock (Limits), once it has sat connected but unaddressed (sysfs state `default`) for 2 s of that wait, at most once per 10 s, and at no other time: it writes the port's sysfs `disable` 1, then 0 a second later, which the kernel runs under the hub's lock, after any enumeration in progress, disconnecting the child before VBUS goes off. Each write and read-back runs in a bounded child; a cycle that fails or is interrupted from the off write on still writes 0, unless one of its children survives SIGKILL and so could still write after it, and says in `hil.log` whether that restored power or was not attempted. The report lists the cycles (`portCycles`).

The battery runs a board only after commissioning sets `reentry` and confirms `uid`; `install` and `restore` work without `reentry`, for commissioning. Only commissioned roster boards can be offered for a run. Adding a board is commissioning, the lead's (`commissioning.md`), never a review-time or dispatch-time action: the runner refuses a build record from a dirty tree, an uncommitted roster entry included.

## Selection

`python3 .claude/skills/build/scripts/check_build.py --select-only (--diff-file <file> | --base <ref> [--worktree]) --hil-config <roster>` adds `hil.{boards, full, uncovered}`. Run the battery when `full` is set or `boards` is non-empty. An empty diff file selects nothing; a caller without the changed-file list passes `--base`. `uncovered` names what no roster board on this host can run; report it, never treat it as covered. An app source (`apps/`, `ports/<port>/apps/`) selects no board and is uncovered, except `dfu_runtime`, which selects the esptool boards of the ports that build it, and leaves uncovered each port that builds it without one (mimxrt10xx today): the battery runs the bootloader with its generated fixture on J-Link and ST-LINK boards and with `dfu_runtime` on esptool boards. The runner, the build scripts it imports, its lock helper's pin and the roster (`.claude/skills/hil-contract/scripts/`, `.claude/skills/build/scripts/`, `lib/agentrc`, `test/hil/*.json`) select every roster board; a wording change to this page selects none.

There are no examples or test names to select: a run is the whole battery on one board, and the board is the only selection.

## Build

```bash
mkdir -p cmake-build/hil
python3 .claude/skills/build/scripts/check_build.py --board <board> --backend cmake --shared --hil-config <roster> > cmake-build/hil/<board>.build.json
```

`<board>` is the roster name, the TinyUF2 board name. An espressif board builds without `--backend cmake`. A fresh worktree, a review worktree included, needs CLAUDE.md's worktree setup (submodules and dependency links) before `check_build.py` can build in it.

The build record is this contract's build receipt: build it on the clean, pinned HEAD with `--hil-config` and pass it with `--build-record`. `--hil-config` binds the build's own flash target to the roster's probe or bridge (build contract); the run refuses a record whose binding names another flasher, and checks the files that target reads against the record. The build dir's lock covers that target only: the files the runner reads itself (the BIN it verifies, the segments it reads back, `apps/blinky.uf2` and `apps/dfu_runtime.uf2`) are copies in the run dir, taken at admission from bytes that hash as recorded, so a rebuild after the target cannot change them. For a J-Link or ST-LINK board it must be a cmake build (`--backend cmake`), whatever backend CI builds the port with; board facts are read from the port's CMake files too. For an espressif board it must be an IDF build from CI's `espressif/idf` image; the run binds its generated `sdkconfig`, `flash_args`, the four segments (bootloader, partition table, otadata, `tinyuf2.bin` in the factory partition) and `apps/dfu_runtime.uf2`, and checks every segment against the generated partition table and the candidate's partition CSV. The run refuses a build record that is not clean, does not match the checkout now (HEAD, submodules, `get_deps` dependencies at their pins), or whose artifacts changed since. Commit first; ESP-IDF's records also go stale at the next commit (build contract).

The Ninja queries that inspect a flash target (`ninja -t commands` at the build, each `ninja -n -v` dry run at the install) are bounded to 30 seconds. At the build, a timed-out query's whole session is killed and its ESP-IDF container (`tinyuf2-query-<pid>`) removed, and the build fails naming the build dir, the query and any container docker still lists. At the install, each query is a tracked child of the runner, its command and output in `hil.log` and only ninja's stdout parsed, and an ESP-IDF query runs in a container named `tinyuf2-hil-<board>-query`. A timed-out query fails the step (`<build dir>: ninja query -n -v <target> timed out after 30s`), its container removed before the build dir's lock is released; a query container docker still lists after the query, or one left by an earlier run, fails the step before the flash and stays tracked, so cleanup removes it by name (on an espressif board the snapshot session has already touched the board).

## Execution

```bash
python3 .claude/skills/hil-contract/scripts/hil_test.py run -b <board> --build-record cmake-build/hil/<board>.build.json <roster>
```

Before taking the lock, the run checks the automount exclusion rule, and every span it could write (the HEX the flash target loads, inside the install span and the device's flash limits and laid out as the BIN; the BIN's board id), with the install and app spans taken from the candidate's source. Run it in the background; one board takes about 2 minutes, and the run is complete when it exits, or when it printed `cleanup.holder.inProcess` true and will not (Recovery): its last stdout line is the report JSON (Results). With several boards, one battery per board, one after another.

The battery's steps on one board, all under one lock. The roster's probe serial selects the board (each probe is wired to one target), so no step identifies the chip:
1. **install:** the record's `tinyuf2-jlink` target runs (`cmake --build <dir> --target tinyuf2-jlink`) under its build dir's lock, once the files it reads hash as recorded and its dry run shows nothing but the flasher; JLinkExe can exit 0 with every command failed, so the transcript must show the record's HEX downloaded (programmed, or skipped as already matching), `O.K.` and the script completed, with no failure line. The files are hashed again after it, and a session of the runner's verifies the BIN at its flash address (`verifybin`), then resets. The board is touched from the target's start; only a transcript that ends at "Connecting to J-Link ...FAILED", before any target connect, leaves it untouched.
2. **dfu:** the UF2 drive with this board's serial is found. On the RT boards the install has left the app start erased on the bench (Limits), so DFU comes up; if it never enumerates, as when a valid app boots (an install on stm32f303disco, stm32f411ve_discovery or stm32h563_nucleo keeps the app; per-board evidence: bench-history.md), the commissioned `retained-register` re-entry brings DFU up (its claim says so); any other DFU failure fails the step. `INFO_UF2.TXT` must name this build's version and board, and `CURRENT.UF2` must have its size. The double-tap register is then cleared and read back, once the bootloader runs.
3. **copy:** a generated app is copied to the drive.
4. **app-ran:** the probe shows the app counting in thread mode with VTOR at the app start.
5. **reenter:** the bootloader is re-entered by the commissioned path, and the drive's `CURRENT.UF2` reads the app back.
6. **cleanup** (reported as `cleanup`, not a step, state `blinky copied`, or `untouched` with nothing to do when no session reached the board): the record's TinyUF2 is installed again as in install, DFU is found, the record's `apps/blinky.uf2` (admitted with the record: one family, every block in the app region) is copied to the drive, and the DFU device must leave and stay away for a quiet period. Any failure keeps the board held (Recovery, exit 4).

On an ST-LINK board the steps are the J-Link board's, each probe session one STM32CubeProgrammer CLI script (`-script`) that connects to the roster's serial in `HOTPLUG` mode, without a reset. A session passes only with exit 0, the roster's Device ID and NVM size, every operation echoed in order with its success line, no `Error` line and the script's end; the CLI stops a script at its first failed operation. `install` runs the record's `tinyuf2-stlink` (`--connect port=swd sn=<serial> --write tinyuf2.hex --go`), whose transcript must show the HEX parsed, the sectors erased, "File download complete" and "Start operation achieved successfully"; a session of the runner's then reads the BIN back from its flash address (`-u`), compares it, and resets (`-rst`). `app-ran` takes both samples, the delay and the image read-back in one script. The SYSRESETREQ write is `-w32 … -nv`: with the CLI's read-back the write fails across the reset. Only "Error: Serial number not found" before any device line leaves the board untouched.

A board's evidence is scoped as the report says. "app-ran" is execution after the bootloader handoff; on a J-Link board a run triggered by the upload alone is unverified (an esptool board's app-ran observes the copied app itself over USB). "reenter" by `retained-register` is the forced-entry path, not a physical double tap.

On an esptool board, each esptool connection is a child of the runner (`esp_session.py`), and so is each USB control request (`usb_dfu.py`, pyusb):
1. **install:** a first connection takes the MD5s of every partition the battery never writes (nvs, ota_1, ffat on the 8 MB layout) as the run's snapshot, kept in the row's `snapshot` however the run ends; that session is the first to touch the board, which only a missing bridge (no tty with its serial), a container left by an earlier flash (a query container left by an earlier run fails the step later, at the dry run), or a failed or interrupted `docker create` of the flash container leaves untouched. Then ESP-IDF's `flash` target runs in CI's image (`cmake --build <dir> --target flash`), with the same lock, hash and dry-run checks as a J-Link install: the bridge's tty is the only device passed in, as `ESPPORT`, with `IDF_FLASH_FULL=1` so ESP-IDF v6 writes segments already in flash too, and the container is named `tinyuf2-hil-<board>` so a survivor is found and ended by name. Its transcript must show every segment written at its offset and hash-verified, then the hard reset. A runner session then reads each segment back and takes those MD5s again, then resets once; the runner compares the read-back bytes with the build's segment files and the MD5s with the snapshot, and any difference fails the step. esptool rewrites the bootloader header from `flash_args`, which the build already holds (dio, 80 MHz, 8 MB): on the bench (2026-10-13, esptool 5.3.1 in espressif/idf:v6.1) all four segments read back identical to the files. The roster's bridge selects the board (it is wired to that board only), so the chip is not identified, and its security eFuses and flash size are commissioning's to check. The evidence lists each write's span and the 4 KiB-aligned span covering it. Blank otadata boots the factory partition, TinyUF2.
2. **dfu:** as above; `INFO_UF2.TXT` reports the app partition (ota_0) as its flash, and no register is written.
3. **copy:** `apps/dfu_runtime` from the record, plus a block carrying a fresh nonce in ota_0's last 256 bytes, where the app reads it, renumbered under one `numBlocks`; the image itself is never patched. The record is refused when the image reaches that block or TinyUF2's 64 KiB flash cache window over it (`FLASH_CACHE_SIZE`) leaves ota_0. The evidence lists the image and nonce spans and the cache windows covering them.
4. **app-ran:** the app enumerates with its own VID:PID and the board's serial on the DFU's USB path, its DFU runtime interface string read from the device is `HIL <nonce>`, and TinyUF2 stays away for a quiet period.
5. **reenter** (`dfu-detach`): DFU_DETACH to the app is acknowledged, the app leaves, TinyUF2 comes back on the same path, and `CURRENT.UF2` reads back the image and the nonce block.
6. **recopy:** a copy with a fresh nonce boots the app again.
7. **cleanup:** as on a J-Link board, with the install as in step 1: the preserved regions' MD5s after the writes, and again after the blinky copy, must equal the run's snapshot (a recovery takes it from the failed report's `snapshot`; a manual `restore` takes its own first). A mismatch fails the cleanup and keeps the hold.

`--fail-at <step>` exists only for acceptance: it fails that step to exercise cleanup.

### CI

The `HIL` workflow (`.github/workflows/hil.yml`) runs the battery on the ci.lan rig for every pull request from this repository (a fork's never reaches the rig). A hosted job selects the boards the change reaches (Selection, with `test/hil/ci.json`) and prints what is uncovered in its summary; the rig job, on the runner labelled `tinyuf2`, checks out the merge commit, fetches the submodules and the roster ports' dependencies, and runs `scripts/hil_ci.py`: per board a record built there (Build) and one battery whose run directory (`run --run-root`) lies under the rig's `hil-state/<run id>` with the record and the battery's output, uploaded as the job's artifact. The battery keeps trying a held board every 15 s within `run --lock-wait` (10 min from CI), then reports it locked, which the job reads as not-run, never a pass; a cleanup holder is never waited for. The job's only pre-flight is its markers and the runner's own probe check: a surviving `mcopy` or USB helper of a killed run is seen through the marker, not by a host-wide process scan. Each row maps onto the Verdicts: the job exits 0 only when every selected board passed, 1 on a fail or not-run, 2 on a blocker. A battery that ended without a report, or kept a cleanup holder, leaves its `<board>.started` marker without a `.done`: that board is a blocker on every later run until recovery (Recovery) has run and the marker is removed by hand; the workflow is never cancelled by a newer push for the same reason. `workflow_dispatch` runs named roster boards, with `fail_at` for `--fail-at` (acceptance only).

## Reservation

Locks are taken through agentrc's `hil` helper, `lib/agentrc/skills/hil/scripts/hil_lock.py`, at the commit the `lib/agentrc` submodule pins (`git submodule update --init lib/agentrc`), never an installed agentrc's copy. `hil_test.py`'s `run`, `install` and `restore` refuse before any hardware access while the submodule is missing, checked out at another commit or locally modified; the manual `hold`, `release` and `status` below run the helper directly, with no such check. The lock is the board's `<lock>` (Hosts/rosters): `hold` and `release` take it and `status` (no board argument) shows it, while `hil_test.py -b` and the probe scripts take the board name.
- **The battery locks itself,** as `hil_test.py`, which the helper's `release` refuses to kill.
- **The lock fails closed.** An unusable lock dir refuses the run (exit 2); it never runs unlocked. `HIL_NO_BOARD_LOCK=1` is the bypass (`hil` Board locks); the report then says `lockBypassed: true`.
- **Manual sessions** (hw-debugger, hw-validator):
  1. Take your own hold: `python3 lib/agentrc/skills/hil/scripts/hil_lock.py hold <lock> --reason "<unique session reason>"`.
  2. Install a build record's TinyUF2, and restore the board when done:

     ```bash
     python3 .claude/skills/hil-contract/scripts/hil_test.py install -b <board> --build-record <record> --under-hold "<reason>" <roster>
     python3 .claude/skills/hil-contract/scripts/hil_test.py restore -b <board> --build-record <record> --under-hold "<reason>" <roster>
     ```

     `install` is the battery's install step from the record (Execution: a J-Link board runs the record's `tinyuf2-jlink` target, an ST-LINK board its `tinyuf2-stlink`, an esptool board takes the four IDF segments), then waits for DFU; it takes the record the battery takes, admitted the same way, so it needs the automount exclusion rule (`commissioning.md`) and a clean build of HEAD. `--try-reentry <method>`, while the roster's `reentry` is unset, gives DFU's fallback (Execution, dfu) for commissioning; `restore` takes it too. `restore` is the cleanup (Execution, step 6), from a clean build record of HEAD. Both refuse unless the hold is provably yours: the record's reason, a live pid, a FLOCK on the lock file in that pid's own fds, and a failing probe of the flock.
  3. Release with `python3 lib/agentrc/skills/hil/scripts/hil_lock.py release <lock>`, only after a `restore` that exited 0 with no `survivors`. Otherwise the board is not cleaned up: keep the hold and report it as a blocker.

  Manual exits: 0 the operation succeeded (for `install`, DFU came up; for `restore`, DFU left after the blinky copy and stayed away); 1 it failed before writing; 2 refused before any hardware access; 4 a child survived SIGKILL, or an `install` or `restore` failed after it began writing: keep the hold.

  On a refused hold, `python3 lib/agentrc/skills/hil/scripts/hil_lock.py status` (no board argument; it prints every holder) gives the holder to report. A `role: cleanup-holder` holder is this contract's exit 4 (Recovery); any other `hil_test.py` holder is a battery run (`hil` Board locks: wait within the budget).
- **Cleanup state** for a hw-validator or hw-debugger dispatch: `restore --under-hold` leaves the board on the record's TinyUF2 with `apps/blinky` copied through it, and its `cleanup.evidence` (DFU left after the copy and stayed away) is the observation that Cleanup records. Blinky running is not checked. Whoever uses the board next flashes it first; tinyusb's HIL does.
- **Lock-wait budget:** htpc has no CI runner, so it is the dev-bench row of chief's budget unless the dispatch names another; ci.lan is the CI-runner row. `run --lock-wait <s>` keeps trying a held board that long, never a cleanup holder; the CI job passes its own (Execution, CI).

## Results

The last stdout line is JSON, also written to its `reportPath`. Its fields:
- `pass`, `caveat`;
- per board: `ran`, `pass`, `locked`, `recoveryBlocker` (a `locked` row whose holder is a cleanup holder), `lockBypassed`, `probeUsers` (pids left on the board's probe, refused after the lock), `firmware` (path, sha256, version, build record), `steps[]` (`step`, `pass`, `evidence`, `detail`), `cleanup` (`pass`, `state`, `evidence`, `heldAfter`, `holder`, `survivors`), `jlinkRetried` (J-Link boards only: sessions run again after a crash before the target connect; Limits), and `detail`;
- `error` on a refusal or an operation failure.

| Exit | Meaning |
|---|---|
| 0 | every board passed and was cleaned up |
| 1 | a board failed or did not run; it was cleaned up or never touched |
| 2 | refused before any hardware access (usage, roster, source, build record, lock helper, lock dir) |
| 4 | cleanup failed; the board is held when `cleanup.heldAfter` (not under `HIL_NO_BOARD_LOCK`). From `install` or `restore`: a child survived, or the operation failed after it began writing; keep your hold |

A delegated run (`hil-operator`) returns `{pass, results, caveat, wedged}` and, beside them, `reportPaths`:
- `reportPaths` maps each board to its JSON's `reportPath`, which a recovery dispatch needs.
- Across several boards (Execution: one battery per board), `results` holds every board's row, `pass` is true only when every run's is, and `caveat` joins the runs' non-empty caveats.
- A launched run that ended without printing its JSON (killed, crashed) may have programmed the board and left it running a candidate. The operator writes `pass: false`, `caveat: "run ended without a report; board state unknown"` and one row per board, exactly `{board, ran: null, pass: false, locked: false, detail}`, with `detail` naming the exit status, the output tail and `python3 lib/agentrc/skills/hil/scripts/hil_lock.py status` at that moment.
- The operator runs the battery once and returns. It never waits on a lock and never retries: a `locked` row comes back as is, and its caller retries under `hil`'s Caller rules, marking a flaky pass `flaky: true`.
- A recovery dispatch runs the `restore` Recovery names for the state (`--recover-holder` for a cleanup holder, `--under-hold` after a run with no report) in the foreground and returns `{pass, results, caveat: "", wedged, exit, error, survivors}`: that JSON's `results`, `error` (`null` when absent) and `survivors` (`[]` when absent), and the exit status. Any exit but 0 is a blocker for the caller. A probe that cannot connect is `needs-user` (the board's recovery note, Recovery).

### Verdicts

Each board's row maps onto the `hil` verdicts, except a commissioning run's (`commissioning: true`, from `--try-reentry`), which is never validation.
- `pass`: `ran`, `pass` and `cleanup.pass` all true;
- `fail`: `ran` and not `pass`, with a failing step, `cleanup.state` other than `untouched`, and that step's `detail`;
- `not-run`: `ran` false (`locked`, a refusal, or a failed probe check: not exactly one esptool bridge tty with that serial), or a failing step with `cleanup.state` `untouched`, with its `detail`. Nothing was written, so the failure is the rig's: no probe with that serial on this machine, or one unplugged or dead;
- a blocker, never a `fail` row: exit 4, `ran: null` (no report), a `locked` row with `recoveryBlocker`, a `probeUsers` row, and an abort, which is `ran` and not `pass` with no failing step (an interruption or an unexpected error, named in the board's `detail`).

`testedHead` is the build record's `input.head`. `regression` is `unknown` unless the battery also ran on the merge base.

## Recovery

- A board whose run ended without a report gets a manual `restore --under-hold` (a recovery dispatch carrying the board and a record, as for exit 4) before its next run, and only once no such process is left on the host. Killing the runner frees its lock but not its children, which `restore` cannot see, and nothing ties a surviving child to the run that died, so the check is host-wide: any other battery, holder or J-Link session also keeps the blocker. Run this as a command of its own, since a shell line carrying the plain name would match itself; none is left when it prints nothing:

  `pgrep -ax JLinkExe; pgrep -ax mcopy; pgrep -af '[h]il_test\.py'; pgrep -af '[e]sp_session\.py'; pgrep -af '[u]sb_dfu\.py'`

  The `hil_test.py` check also covers the runner's `fat-read` subcommand. While a process is left, or this cannot be established, the blocker stays.

Exit 4, a cleanup holder:

- The board stays held by a detached holder forked from the run: reason `hil_test.py`, `role: cleanup-holder`, with its pid in `cleanup.holder`. It ignores SIGTERM and SIGINT, so a timeout kill cannot free the board; only recovery releases it. It re-executes itself without `RUNNER_TRACKING_ID`, the variable under which a GitHub Actions runner kills every process still alive when its job ends; a holder whose re-execution failed, or the in-process holder below, keeps it and dies with the job: the board is then unheld and not cleaned up, which `hil_ci.py`'s marker records (Execution, CI), and recovery is a `restore --under-hold` under a fresh hold, as for a run without a report.
- If no holder could be forked, `cleanup.holder.inProcess` is set and the runner itself is the holder: it prints the report, closes its stdio and does not exit until recovered, so no completion notice arrives. When a run's notice is overdue, read the task's output: a final JSON line with `cleanup.holder.inProcess` true is this case. Do not wait for its exit.
- `cleanup.survivors` lists children that outlived SIGKILL (a J-Link, mtools or FAT read stuck on the device), and a flash or dry-run container that outlived `docker rm -f` (`{"container": "tinyuf2-hil-<board>"}` or `{"container": "tinyuf2-hil-<board>-query"}`); recovery refuses while any of them is still alive. A runner killed outright leaves its containers to run out; the next install refuses while `docker ps -a` lists the flash container, and its dry run fails while it lists the query container, which that run's cleanup then removes. Each child runs in a session of its own and the kill reaches the whole session, so a JLinkExe that ninja runs in a process group of its own under the flash target is killed and reported too.
- The holder may stand for a stuck J-Link or mtools process; tinyusb's reflash does not make the board safe, and it is out of service until recovered.
- Recovery is a separate `hil-operator` dispatch under `hil`'s Board locks scope, carrying the board, its holder pid, the failed run's `reportPath` and the release. After process, probe and host readiness are established, it runs:

    `python3 .claude/skills/hil-contract/scripts/hil_test.py restore -b <board> --build-record <record> --recover-holder <pid> --report <reportPath> <roster>`

    `<record>` is the failed report's `firmware.buildRecord`, or a record rebuilt on the clean HEAD when it no longer verifies. The command proves that pid holds the board as the failed run's cleanup holder and that none of the run's survivors and no J-Link process on the probe is alive, restores the board while the lock stays held, and only then releases the holder. On an esptool board the restore checks the preserved regions against the snapshot in the failed report, and recovery is refused for a touched run without one or one whose regions differ from the checkout's. A candidate whose drive cannot take the blinky copy fails the restore; the board stays held until a record that can restore it is given. A second recovery of the same board while one runs is refused (exit 2).
- If the probe cannot connect, recovery is the human's: on imxrt1060_evk, serial download mode (BOOT_MODE 01: SW7 OFF OFF OFF ON, inferred from the EVK guide), and on imxrt1064_evk the same switch (SW7, MIMXRT1064-EVK schematic sheet 16), on the ci.lan rig, where tinyusb's roster also gives the board an OpenOCD recovery flasher; on espressif_esp32s3_devkitc_1, ROM download mode: hold Boot (SW1, GPIO0 low), press and release RST (SW2, CHIP_PU), then release Boot (DevKitC-1 schematic V1.0; the TRM's strap table also needs GPIO46 low, its default pull-down); on espressif_p4_function_ev, the same with BOOT (SW2, GPIO35 low) and RST (SW1, CHIP_PU) (Function-EV-Board schematic rev 1.4); on stm32h563_nucleo, a power cycle: unplug and replug its STLINK USB (CN1), which powers the board (bench-history.md).

## Limits

Measurements and dated bench observations behind these limits, loader footprints included, live in `bench-history.md` beside this page.

- Covered: imxrt1060_evk, metro_m7_1011, stm32f303disco, stm32f411ve_discovery, stm32h563_nucleo, espressif_esp32s3_devkitc_1 and espressif_p4_function_ev on htpc; imxrt1064_evk on ci.lan. Not covered: ports without source facts in the runner, lpc55 among them (no battery, `install` or `restore` for lpcxpresso55s69), espressif chips other than the ESP32-S3 and ESP32-P4, self-update, an interrupted update, malformed UF2 input, the physical double tap, and TinyUF2's write protection on the STM32 boards: a battery runs F303 unprotected after any option-byte reload until a power-on reset, leaves F411's protection set, and the H5 sets none today; on the H5 the runner never removes protection and an install that meets it fails.
- On ci.lan, imxrt1064_evk's probe (1-1.1) and its USB (1-1.2) share one hub, the farm's cabling, where commissioning.md asks for separate hubs: a device hung mid-write there could stall the probe connect too (Shared hubs below). Its silicon revision was not read from the marking (the rig is remote); the A and B errata were both checked. Whether its FlexSPI configuration observes ERR011377 (a delay after the DLL lock before the first flash access, IMXRT1064CE_A Rev 1.3 and IMXRT1064CE_B Rev 1.1) is unchecked: pending, not a found defect. Every install leaves [0x7000C000, 0x70010000) erased, an inference from one sample (bench-history.md, imxrt1064_evk), as on the RT1060 boards.
- The `usbPower` port cycle (Hosts/rosters) runs under the board's own lock, a limitation of `hil`'s rig-wide rule, not an exemption. On the Port Authority hub (5-3) a cycle re-enumerated only its own port's device when measured; neither a VBUS drop nor an enumeration storm was measured (bench-history.md: Shared hubs). On a ganged hub (5-1, 5-2) a port cycle removes no power while another port in the gang is powered, and can power the whole gang off when it is the last, so `usbPower` must not name a port there. On the Port Authority hub's USB2514B a full- or low-speed device that detaches and re-attaches within 100 µs of SE0 may not register as a detach (USB251xB errata, module 4); stm32f303disco's missing disconnect is instead its board's fixed D+ pull-up, by design (bench-history.md: stm32f303disco). Never cycle a rig hub port with `uhubctl` or a raw hub request: a cycle that met an enumeration in progress killed an xHCI controller. Another board's enumeration errors on the same hub can reset a neighbour mid-read, and `install`'s FAT read then times out (exit 4) (bench-history.md: stm32h563_nucleo). A device hung mid-write stalled a J-Link connect on the same hub.
- esptool boards: the runner needs esptool 5.2.0 and pyusb with libusb-1.0 for its own Python. Re-entry by DFU_DETACH is the only method built; the GPIO0 detection window is not. The bridge's UART carries every esptool session. A helper that survives SIGKILL is handled like a stuck J-Link, but no way to wedge one on the board was found, so that path is unit-tested only. The host log shows a USB reset and block-device read errors at the end of a UF2 copy, and on the P4 a full-speed device that never answers while an esptool session holds the chip; the battery passed with the latter.
- Every probe and USB path is unverified until commissioning has run on the board, and commissioning is manual.
- cmake builds pass `TUF2_LOG=0` unless `LOG` is set, as make does, so the HIL image does not log on the board UART.
- `install` from a blank board, or one whose ROM found no boot image, brings up DFU on imxrt1060_evk and metro_m7_1011; until a `loadbin` has run, a new J-Link session reads such a board's flash wrong.
- That every install on the RT boards leaves the app start erased is an inference from samples, not a measurement of every image.
- Of a port's CMake flash targets the runner runs only `tinyuf2-jlink`, `tinyuf2-stlink` and ESP-IDF's `flash`, bound by the record to the roster's probe or chip (the bridge's tty is passed at flash time). Never use the erase targets on a rig board (`tinyuf2-erase-external-jlink` erases [FLASH_BASE, FLASH_BASE + 64 KiB), the bootloader with it), nor ESP-IDF's `combined-flash`, which has no port selection and writes nvs and both OTA slots blank.
- stm32f411ve: runner sessions connect as `Cortex-M4` (`SESSION_DEVICE`) because a `-device stm32f411ve` connect resets the chip and drops DFU, and the install's verify session waits 1 s before its halt (`INSTALL_SETTLE_MS`).
- Double-tap retention: on stm32h563_nucleo the word survives a system reset only with option SRAM1_3_RST=1 (set on this chip); on stm32f303disco and stm32f411ve_discovery its survival across SYSRESETREQ is undocumented and inferred from commissioning.
- stm32f303disco signals no disconnect when TinyUF2 comes up after a reset, so `stays_away` (the control trial's, the copy's) and `observe_app` cannot see a transient DFU entry there; its roster `usbPower` covers DFU (Hosts/rosters).
- stm32h563_nucleo: STM32CubeProgrammer behaviour the runner relies on is bench-observed on v2.23.0 only (UM2237 not in the library).
- A `JLinkExe` crash inside the target is not retried (the crash retry below covers the runner's own sessions only): it fails the install, touched.
- `JLinkExe` sometimes crashes in `libjlinkarm` at the probe connect on htpc, cause unknown. A session that crashed this way, before the target connect, runs once more after 2 s (`jlinkRetried`); a second crash fails the run.
- No reproducer for an instrumented build: the battery and `install` take only a clean build record. A claim that needs one is reported pending.

Commissioning a board follows `commissioning.md` beside this page.
